# 편집 지연 및 완결성·출처 단계 — 진단만

사용자 추가 보고: 최초 분석은 약 3분 후 완료되지만 조항별 검토 수정 중에도 계속 느림. ‘문서 완결성·출처’의 의미와 완결성 기능 제외에 따른 단순화를 질문함. 이번 진단으로 성능 엔진이나 완결성 기능을 제거하지 않음.

## 확인한 코드 경로

- 연결 조항 선택 변경은 bindReassign에서 runAnalysis를 호출함. 단순 표시 위치 변경도 전체 분석 경로로 진입함.
- 일반 조항의 판정 클릭·메모 change는 해당 행과 제안·리포트를 갱신함. 항상 전체 계약 매핑을 재실행하는 것은 아님.
- 계약 전반·부속서류 관련 블록과 직접 의견 편집 경로에는 renderClauses 전체 재렌더가 있음.
- 메모 입력마다 manualInputKeyV3를 확인하고, 저장은 250ms 병합됨. 내부 평가자료 저장이 켜져 있으면 추가 600ms 후 standardPacket 생성·저장·출처 갱신이 발생함.
- 분석 Worker의 ‘문서 완결성과 출처 연결’ 한 단계에 Integrity.analyze, JudgmentSources.compile, 항목별 JudgmentHints.retrieve 및 DecisionReferences.retrieve가 섞여 있음. 해당 표시에서 오래 걸렸다는 이유만으로 Integrity가 주범이라고 판단할 수 없음.
- high confidence 완결성 발견사항은 pendingReviewItems에 들어가므로 미처리 시 검토 완료를 막을 수 있음.

## 합성 편집 재현

build/diagnose_review_interaction.mjs, 격리 Chrome, 페이지 CPU 4배 지연, 태그 문서 500건·고유 근거 26,000행·코퍼스 29건, 등록 표준 0개. 14개 문구를 반복한 합성 계약이며 실제 폐쇄망 자료와 같지 않음. 계측용 함수 래퍼 때문에 시간은 참고값임.

| 계약 | 최초 분석 | 판정 클릭 동기 처리 | 메모 입력 일괄 이벤트 | 메모 change | 평가 패킷 생성 |
|---|---:|---:|---:|---:|---:|
| 2,821자·57조각 | 3,378ms | 22.9ms | 2.2ms | 10.1ms | 30.8ms |
| 14,106자·281조각 | 3,647ms | 28.9ms | 2.4ms | 11.8ms | 39.5ms |

두 경우 모두 조항 재지정 시 전체 분석 호출 1회를 확인함. 일반 판정·메모 경로는 전체 분석 호출이 없었음. 수분 단위 편집 지연은 이 합성 조건에서 재현되지 않음. 표준자료 규모·추출 구조·다른 편집 경로와 실제 실행 환경은 추가 확인 필요.

## 기능 정리 제안 — 아직 구현하지 않음

문서 완결성은 조문번호·중복·내부참조·별첨 등 문서 형식의 자동 오류 후보 탐지임. 조항별 계약 검토의 핵심 판정과 분리 가능함. 현재 오탐과 완료 차단 부담을 고려하면 자동 점검·알림·완료 제한을 제품에서 제외하는 방향이 합리적임. 기존 사용자가 직접 쓴 완결성 의견·이력은 보존해야 함.

텍스트 추출·조항 분할·본문과 별첨 구역 구분, 자동판정 근거의 본건 원문 확인까지 삭제하는 것은 다른 문제임. 이들은 유지해야 함. 출처 단계의 과거자료 연결·참고 검색은 자동판정 근거 유효성 검사와 구별하여 별도 진행 표시와 비용 측정이 필요함.

완결성 제거가 사용 흐름을 간단하게 할 수는 있으나 3분 지연과 편집 지연을 모두 해결한다고 주장할 근거는 없음. 조항 재지정의 전체 분석 재호출, 전체 재렌더·저장 후 후속 작업도 별도 개선 대상임.
