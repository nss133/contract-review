# contract-review UX 감사 + 재설계안

작성: 2026-07-29 · 대상: dist/contract-review.html (main @ 0f46231) · 방법: 실제 앱 구동(IT용역 골드셋 계약 주입, 1440×900) + src/app.js·template.html·style.css 정독

## 1. 감사 결과 (측정 기반)

측정 시나리오: IT용역 위탁계약서(24조항, 6,860자) 붙여넣기 → 분석 시작 → 첫 검토 시도.

### 1.1 분석 후 랜딩이 결론을 주지 않음 (스크린샷 02)
- 분석 완료 후 체크리스트 탭에 머무름. 리포트 탭은 활성화만 될 뿐 사용자가 직접 이동해야 함(+1클릭).
- 랜딩 화면 첫 스크린에 결론·수치가 전혀 없음: 접힌 입력 패널 → 필터 5종 → 파란 모듈 칩 16개 → 형식 점검 칩 → 심각도 범례 → 그제서야 표 시작.
- 표는 95행 중 88행이 "—"(이번 분석과 무관한 비활성 모듈 항목). 신호 7행(검토제안 1·반영 2·기타 4)이 소음 88행에 묻힘. 전체 문서 높이 11,108px(약 12스크린).

### 1.2 리포트가 "검토 개요"가 아님 (스크린샷 03, 09)
- 좌측 절반이 계약서 전문 재게시임. 첫 화면은 표제부 공백·자리표시자("OOOO", 빈 줄)로 채워져 정보량 0.
- 결론 배너 1줄은 좋으나 그 아래에 핵심 수치 집계(반영 n · 제안 n · 검토제안 n · 판정 진행 n/n)가 없음. 숫자는 결론 문장 안에 산문으로만 존재.
- 우측 컬럼은 max-height 82vh 내부 스크롤(1,748px) — "한 화면 파악"이 아니라 이중 스크롤.
- 하단 액션 영역에 7개 컨트롤 혼재: 일상 액션(검토의견 내보내기)과 관리 액션(코퍼스 백업·복원, 판정파일 일괄 반영, 지식 반영, 골드셋 저장)이 같은 위계로 나열됨.

### 1.3 조항별 보기 — 클릭 탐색 강제 (스크린샷 04, 05, 06)
- 초기 진입 시 우측 패널 완전 공백(화면 절반이 빈 공간). 무엇이 나올지 힌트 없음.
- 좌측 목록 첫 카드가 "(전문)" — 공백·자리표시자만으로 첫 스크린 전체를 차지함.
- 조항을 클릭해야 우측 상세가 보임. 클릭 후에도 상세 패널에 어느 조항의 상세인지 표기가 없어, 좌측을 스크롤하면 우측이 어느 조항 것인지 알 수 없음(스크롤 동기화 없음).
- 최고 우선순위인 "⚠ 검토 제안" 진입 카드가 조항 목록 최하단(6,048px 스크롤 끝)에 있음.
- 일괄 판정 바(통과계약 모드)가 개별 판정 전인 최초 진입부터 최상단에 노출 — 절차상 "예외 먼저 개별 판정 후 사용"인데 위치가 반대임.

### 1.4 검수 탭 — 기본 뷰가 소음 (스크린샷 07)
- 225카드 · 문서 높이 75,891px(약 84스크린). 기본 필터 "전체"가 전량 렌더.
- 최상단 연속 카드가 전부 "실무 항목 — 검수 대상 아님"(검수 불가 카드 38개가 목록에 섞임).
- 진행 상태가 확인 186/수정필요 1/미검수 0 — 사실상 완료인데 완료 요약·다음 행동 안내가 없고 225카드를 그대로 보여줌.

### 1.5 도구 위계 혼재 — 변호사용 vs 큐레이터용
- 탭 5개가 동일 위계: 체크리스트·조항별 보기·리포트(매 검토 사용) vs 검수·골드셋(지식 관리자·회귀 채점용, 골드셋 탭은 케이스 미로드 시 빈 화면 — 스크린샷 08).
- 모듈 칩이 두 곳에 이중 표시됨: 입력 패널 안(토글형, 분석 후엔 접혀 숨음)과 체크리스트 상단(표시 전용, 전부 파란 `on` 스타일). 같은 생김새·다른 기능 — 표시형 칩을 눌러도 반응 없음.
- 판정(이상없음/검토의견/해당없음) 컨트롤이 조항별 보기·제안사항 패널에만 있고 체크리스트 표 상세에는 없음 — 표에서 검토하다 판정하려면 탭 이동 필요.

## 2. 정보 구조 재설계

### 2.1 탭 순서·이름 (오너 지시 반영)

```
[리포트]  [조항별 검토]  [체크리스트]     ····(우측 끝, 시각적 분리)···· [관리 ▾]
                                                        └ 지식 검수 · 골드셋 채점
```

- 리포트를 첫 탭으로. 분석 완료 시 자동으로 리포트 탭으로 이동(현행 `runAnalysis()`의 `checklist` 강제 이동을 `report`로 교체).
- "조항별 보기" → "조항별 검토"로 개칭(보기가 아니라 판정을 찍는 작업 공간임을 명시).
- 검수·골드셋은 "관리" 그룹으로 우측 분리(드롭다운 또는 시각적 간격 + 회색 톤). 탭 자체는 유지하되 매일 쓰는 3탭과 위계를 다르게 함.

### 2.2 입력 영역 위치 (분석 전/후 상태)

- 분석 전: 리포트 탭이 입력 화면을 겸함. 첫 화면 = 드롭존 + 분석 시작 버튼 + 부속서류. 별도 탭 이동 없이 "계약서를 넣으면 바로 리포트"가 성립함. 조항별 검토·체크리스트 탭은 빈 상태 안내("리포트 탭에서 계약서를 분석하세요")만 표시.
- 분석 후: 입력 영역은 리포트 상단의 한 줄 요약 바로 축소("IT용역 위탁계약서 · 24조항 · 감지: 조달(근거어: …) [유형변경 ▾] [모듈 조정 ▾] [다시 분석]"). 유형·모듈 조정 UI는 이 바의 펼침 안으로 이동 — 현행 "접힌 입력 패널을 다시 열어야 모듈 토글이 보이는" 문제 해소. 모듈 칩 이중 표시(체크리스트 상단 표시형 칩)는 삭제.

### 2.3 분석 후 랜딩 시퀀스

1. 분석 시작 클릭 → 리포트 탭 자동 표시(0클릭).
2. 첫 스크린 = 결론 배너 + 수치 타일 + 보완 필요 목록(아래 §3).
3. 리포트의 각 항목에서 해당 조항으로 딥링크(클릭 시 조항별 검토 탭의 그 조항 위치로 스크롤) — 개요→상세 동선을 명시적 링크로 연결.

## 3. 리포트 = 일목요연한 검토 개요

원칙: 첫 스크린 안에 "이 계약이 어떤 상태인지"가 전부 담김. 계약 전문은 리포트에서 제거(전문은 조항별 검토 탭의 1단이 담당). 아래로 갈수록 상세·저빈도.

```
┌────────────────────────────────────────────────────────────────┐
│ 결론  필수(본질) 항목은 관련 조항에 닿음. 제안 6건 검토 요.        │  ← 현행 결론 배너 유지
├──────────┬──────────┬──────────┬──────────┬──────────────────┤
│ ✓ 반영    │ △ 제안    │ ! 검토제안 │ 형식 경고  │ 판정 진행         │  ← 수치 타일(신설)
│    2      │    6      │  1(필수0) │    1     │  0 / 9           │     클릭=해당 섹션 앵커
├──────────┴──────────┴──────────┴──────────┴──────────────────┤
│ 1. 보완 필요 — 필수 미확인 (0)           [없으면 한 줄로 축약]     │  ← 최우선, 항상 최상단
│ 2. 검토의견 개진 (n)                    [판정 찍은 내용 요약]     │
│ 3. 제안 (6) — 항목명 · 근거조항 · 원문발췌 · [판정 버튼]          │  ← 리포트에서 바로 판정 가능
│ 4. 부속서류 커버 (n) · 별첨 참조 (n)                             │
│ 5. 형식 점검 경고 (1)                                           │
│ ▸ 특수 규제 확인 (접힘) · ▸ 참고 별첨 (11, 접힘)                  │
├────────────────────────────────────────────────────────────────┤
│ 내보내기: [검토의견 내보내기] [인쇄]                              │  ← 일상 액션만
│ ▸ 팀·지식 관리 (접힘): 지식 반영 · 골드셋 저장 · 판정파일 반영 ·    │  ← 관리 액션 격리
│    코퍼스 백업/복원 · 지식 정규화 후보                            │
└────────────────────────────────────────────────────────────────┘
```

- 내부 스크롤(max-height 82vh) 제거 — 리포트는 페이지 자체 스크롤 1개만.
- 수치 타일은 기존 coverage 색 체계 그대로(녹/청/황/적) — 신규 색 도입 없음.
- 제안 항목에 판정 버튼을 넣어 "리포트만으로 가벼운 계약은 검토 완결" 가능하게 함(현행 verdictControlHtml 재사용).
- 계약 전문+검토의견 대조가 필요한 인쇄용 산출물은 인쇄 시에만 좌측 전문 컬럼을 합성(현행 report-doc 렌더를 print 전용으로 이동)하거나, 조항별 검토 탭 인쇄로 대체.

## 4. 조항별 검토 = 삼단 연속 스크롤

원칙: 클릭 탐색 제거. 계약서를 위에서 아래로 읽는 흐름 그대로, 세 단이 같은 조항 행에 정렬되어 함께 흐름.

### 4.1 컬럼 구성

```
┌─ 헤더(고정) ─ 진행: 판정 9/9 · [일괄 판정 ▾] · [내보내기/불러오기] ──┐
├───────────────┬───────────────────┬───────────────────────────┤
│ ① 계약서 원문   │ ② 검토된 내용        │ ③ 제안 사항                 │
│ (2fr)         │ 반영·제안 (1.2fr)    │ 검토제안·의견 (1.2fr)        │
├───────────────┼───────────────────┼───────────────────────────┤
│ 제7조(지체상금) │ ✓ 반영 SP-DEL-05    │ (이 조항 제안 없음 — 흐림)    │
│ 본문 전문…     │ △ 제안 SP-DEL-06    │                           │
│               │  각 항목: 라벨·근거·   │                           │
│               │  [이상없음|의견|해당없음]│                          │
├───────────────┼───────────────────┼───────────────────────────┤
│ 제8조(지적재산권)│ …                  │ …                         │
│  …조항 흐름 계속…                                                │
├─ 최하단 ──────┴───────────────────┴───────────────────────────┤
│ ⚠ 계약서에서 확인되지 않은 항목 (검토제안 n) — 조항 무관 블록        │
└───────────────────────────────────────────────────────────────┘
```

- 구현 단위는 "조항 행(row)" 하나에 3셀(grid). 컬럼 3개를 따로 스크롤시키는 방식이 아니라, 행 단위로 묶어 한 스크롤로 정렬 동기화를 구조적으로 보장함(스크롤 동기화 코드 불요).
- ①은 현행 .clause 카드 본문, ②는 renderCompareItem(addressed+verify), ③은 현행 "함께 살펴볼" 중 판정 대상·검토의견 기재분. ②③이 빈 조항은 셀을 흐리게(placeholder 한 줄) 두어 행 리듬 유지.
- 검토 제안(부재 알람)은 특정 조항에 속하지 않으므로 최하단 전용 블록 유지하되, 상단 헤더에 "⚠ 검토제안 n건" 앵커 버튼을 두어 6,000px 스크롤 없이 즉시 점프.
- 상단 고정 헤더에 판정 진행률(n/n)과 일괄 판정을 배치. 일괄 판정은 드롭다운으로 접어 1차 노출을 줄임(절차상 후행 도구임을 위치로 표현).
- "(전문)" 조항: 표제부·서명란 등 검토항목 매칭이 없는 세그먼트는 기본 접힘(제목 한 줄 + 펼치기) — 첫 스크린 낭비 제거. 리포트 좌측에서도 동일 적용.

### 4.2 긴 계약서(100+ 조항) 렌더 전략

- 현재 24조항에서 리스트 높이 6,048px — 100조항이면 25,000px+ 예상. DOM 자체는 행당 수백 노드 수준이라 300조항까지는 일괄 렌더로 무리 없음(오프라인 단일 파일, 가상 스크롤 라이브러리 불가 전제).
- 1차: 전량 렌더 + `content-visibility: auto; contain-intrinsic-size` (CSS만으로 오프스크린 렌더 비용 제거, 외부 의존성 0).
- 2차(필요 시): IntersectionObserver로 ②③셀 내용을 지연 채움(행 골격은 먼저, 카드 HTML은 근접 시).
- 탐색 보조: 좌측 얇은 미니맵(조항 번호 목차, 상태 점 색: 반영/제안/의견) 고정 — 100조항에서 특정 조항 점프용. P2 후반 옵션.

### 4.3 판정 컨트롤 배치

- ②③ 각 카드 안 현행 3버튼+코멘트 유지. 판정 시 행 좌측 경계색으로 상태 반영(찍은 항목이 시야에서 구분되게).
- 과거 판정 분포·추천 코멘트(loop)는 기본 접힘(1줄 요약 "과거 이상 100% ▸")으로 축약 — 카드 높이를 줄여 연속 스크롤 밀도 확보.

## 5. 체크리스트 탭 (보조 탭으로 강등 후 정비)

- 역할 재정의: "전 항목 감사 뷰"(필터·검색으로 특정 항목을 찾는 용도). 리포트·조항별 검토가 주 동선이 된 뒤에도 존치 가치 있음.
- "—" 88행 문제: 기본값을 "이번 분석 관련 항목만"으로 필터(coverage 있는 것 + consider). 전 항목은 토글로.
- 표 상세(행 펼침)에 판정 컨트롤 추가 — 어느 탭에서 보든 판정 가능하게 일관화.
- 표시 전용 모듈 칩 바(#checklist-modules) 삭제 — 활성 모듈은 리포트 요약 바에서만.

## 6. 검수·골드셋 평가와 개선안

한 줄 판정 — 검수: 큐레이터 도구로서 기능은 완결이나 기본 뷰가 소음(84스크린)이라 "관리" 영역으로 강등 + 미검수 우선 뷰가 필요함. 골드셋: 순수 회귀 채점 콘솔로 변호사 일상과 무관 — 관리 영역 이동 + 빈 상태 안내 보강이면 충분함.

| # | 문제 (측정) | 개선 |
|---|---|---|
| V1 | 기본 필터 "전체"로 225카드·75,891px 전량 렌더 | 기본 필터를 "미검수만"으로. 미검수 0이면 완료 요약 카드("187건 검수 완료 · 수정필요 1건 보기")만 표시 |
| V2 | "검수 대상 아님" 실무 카드 38개가 목록 최상단 혼입 | 목록에서 제외하고 "실무 항목 n건(검수 대상 아님)" 한 줄 집계로 대체 |
| V3 | 수정필요 1건을 찾으려면 필터 변경 필요 — 완료 상태에서 다음 행동 불명 | 진행 바를 "확인 186 · 수정필요 1(보기) · 미검수 0" 클릭형으로 — 숫자가 곧 필터 |
| V4 | 유형 필터가 검토 맥락과 무관하게 초기화 | 유지(경미). 유형별 미검수 카운트를 옵션 라벨에 병기 |
| G1 | 케이스 미로드 시 빈 화면 — 케이스 만드는 법이 리포트 탭에 있다는 사실을 텍스트로만 안내 | 빈 상태에 절차 3단계 카드(① 리포트에서 케이스 저장 → ② 공유폴더 축적 → ③ 여기서 채점) + "리포트로 이동" 버튼 |
| G2 | 채점 결과(통과/변화/실패)에서 "변화" 케이스의 후속 행동(재저장으로 기준 갱신)이 각주 수준 | 변화 케이스 카드에 "이 결과를 새 기준으로 저장" 버튼을 직접 배치(케이스 JSON 재생성 다운로드) |
| G3 | 골드셋·검수가 일상 탭과 동일 위계 — 첫 사용자 혼란(스크린샷 08) | §2.1 "관리" 그룹으로 이동, 탭 라벨을 "지식 검수"·"골드셋 채점"으로 목적 명시 |
| 공통 | 리포트 하단 관리 버튼 5종(코퍼스 백업/복원·판정파일 반영 등)이 일상 액션과 병렬 | §3 하단 "팀·지식 관리" 접힘 섹션으로 격리 |

## 7. 시각 디자인 방향

제약: 오프라인 단일 파일(외부 폰트·CDN 불가), 기존 배지·심각도 색 체계 유지. 방향은 "정리"이지 "리브랜딩" 아님.

- 타이포 스케일 통일: 현재 11/11.5/12/12.5/13/13.5/14/14.5/15/16px 혼재(10단계). 4단계로 축약 — 12(메타·배지) / 13(본문 보조) / 15(본문·항목명) / 17(섹션 제목). line-height 1.5 통일.
- 간격 체계: 4px 배수 그리드(8/12/16/24)로 카드 패딩·마진 통일. 현재 6·7·10·14·18px 혼재.
- 색 정리: 의미색은 현행 4계열 유지(녹=반영/확인, 청=제안, 황=검토제안/주의, 적=필수/불일치). 회청 중립(#4a5b73 계열)은 별첨·메타 전용으로 고정. 배지 배경은 현행 파스텔 유지하되 동일 의미=동일 색을 전 탭에 강제(예: cov-verify 청과 verify-col 청의 톤 차이 제거).
- 칩 문법 분리: 토글 가능한 칩(모듈)만 파란 채움. 표시 전용 정보는 채움 없는 회색 외곽선 또는 텍스트 배지로 — "눌러도 되는 것"과 "정보"를 형태로 구분(§1.5 이중 칩 문제의 시각적 해법).
- 밀도: 전문가용이므로 여백 확대보다 행 리듬 통일이 우선. 카드 경계선(#e0e2ee)·좌측 상태 보더(4px) 문법은 유지.
- 다크모드는 범위 외(폐쇄망 인쇄 워크플로우 고려 시 라이트 고정이 합리적).

## 8. 구현 단계 제안

| 단계 | 내용 | 규모(예상) |
|---|---|---|
| P1 | 탭 순서 변경(리포트 첫 탭)·분석 후 리포트 자동 이동·입력 영역을 리포트 탭으로 이전·요약 바(유형/모듈 조정 포함)·리포트 수치 타일+섹션 재배열·관리 액션 접힘 격리 | template.html 구조 + app.js 렌더 순서 중심, 중규모(2~3일). 매처·데이터 무변경 |
| P2 | 조항별 검토 삼단 연속 스크롤: 행 단위 grid 재구성, showClause 클릭 모델 제거, 검토제안 앵커, 고정 헤더(진행률·일괄판정 드롭다운), (전문) 접힘, content-visibility | renderClauses 전면 재작성, 대규모(3~5일). verdict 로직 재사용 |
| P3 | 검수·골드셋 개선(V1~V3·G1~G3)·관리 그룹 탭 분리·체크리스트 기본 필터·표 상세 판정 컨트롤 | 소~중규모(1~2일) |
| P4 | 시각 폴리시: 타이포·간격 토큰화(CSS 변수), 칩 문법 분리, 배지 톤 통일, 미니맵(옵션) | CSS 중심, 소규모(1일) + QA |

각 단계는 독립 배포 가능. P1만으로도 "계약서를 넣으면 바로 개요가 보인다"는 오너 요구의 핵심이 충족됨. 골드셋 회귀(기존 케이스 채점)가 P2의 매처 무변경을 검증하는 안전망으로 사용 가능함.
