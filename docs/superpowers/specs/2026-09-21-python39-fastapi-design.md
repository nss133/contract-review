# Python 3.9·FastAPI 전환 설계

작성일: 2026-09-21. 상태: S0·S1 기반 구현 중. 이 문서는 전체 전환 완료를 의미하지 않는다.

사용자 추가 조건: DB는 SQLite로 추정하며 동시 사용자는 10명 이하. 개발은 서버 로컬 SQLite·관리자 발급 계정으로 진행하고, 실제 서버 OS·DB 경로·패치와 배포 정책은 확인 전까지 미확정으로 둔다.

## 1. 확정 조건과 작업 범위

사용자 조건은 Python 3.9, FastAPI, 프론트엔드·백엔드 분리, 현재 화면 구성 유지, 폐쇄망 공용 서버에 설치하여 팀원이 접속하는 방식이다. 비교 기준은 v1.90.8 커밋 4a2e5f195ae9cd23f46bd24cf3ff034453391d80이다.

- 입력·체크리스트·삼단 검토·리포트·지식·평가·관리 화면의 구성, 문구, 버튼, 이동 동선을 유지한다.
- 프론트는 기존 HTML/CSS/JavaScript를 분리·재사용한다. 이번 전환에서 React·Vue 등 새 프레임워크를 도입하지 않는다.
- 백엔드는 Python 3.9에서 실행되는 FastAPI 서비스로 구현한다. 분석·판정·문서 추출·검색·영구저장·자료 입출력의 권한 있는 결과를 담당한다.
- 최종 제품은 Node 프로세스나 JavaScript 실행기를 호출하여 핵심 엔진을 대신 실행하지 않는다. 기존 JS는 개발 중 비교 기준으로 사용한다.
- 이번 전환의 완료 범위는 기존 기능의 이전, 저장·작업 관리, 공용 서버에 필요한 로그인·계약별 접근권한·변경이력·동시 편집 충돌 처리이다. 신규 OCR, 신규 LLM, 폴더 일괄 분석 화면, 실시간 공동 편집·메신저 알림은 별도 확장으로 둔다. 기존 일괄 평가·로컬 AI 기능은 유지 대상이다.
- 배포는 폐쇄망 공용 서버로 확정한다. 팀원 PC에는 Python 설치 없이 브라우저로 접속한다. 동시 사용자는 10명 이하이다. 서버 OS·아키텍처·SQLite 저장 경로·자료량은 S0에서 확인할 환경 항목이며 Windows 서버라고 추정하지 않는다. 인증은 우선 관리자 발급 계정이다.

프론트와 백엔드는 별도 시작 명령, 별도 산출물, 별도 테스트를 가진다. 운영에서는 사내 정적 웹서버/역방향 프록시가 프론트를 제공하고 /api/v1을 FastAPI로 전달한다. 브라우저 기준으로 같은 origin을 사용하더라도 프론트 빌드와 API 프로세스는 독립한다. Python 서버가 프론트 HTML을 생성하지 않는다. 개발에서는 프론트 127.0.0.1:8765, API 127.0.0.1:8766 등 별도 포트로 분리 시험한다.

운영 웹서버는 사내 허용 제품·서버 OS에 맞춰 선정한다. API·작업 프로세스는 서버 서비스로 등록하여 자동 시작·재시작·정상 종료를 관리한다. API/DB 포트를 사용자 PC에 직접 공개하지 않는다. 프론트는 설정된 API 주소와 버전 계약만 사용하며, 서버 OS나 DB 종류를 알 필요가 없다. [FastAPI 프록시 배포](https://fastapi.tiangolo.com/advanced/behind-a-proxy/)

브라우저에는 표시·선택·입력 검증을 남긴다. 최종 자동판정, 완료 가능 여부, 실제 저장 성공 여부는 API 응답으로 결정한다. 브라우저가 전송한 자동 이상없음 값은 그대로 신뢰하지 않는다. 프론트에서 동일 규칙을 재실행하는 이중 엔진은 최종 제품에 남기지 않는다.

## 4. Python 3.9 의존성 기준

FastAPI 시작 기준은 0.128.8이다. 공식 릴리스 기록상 0.129.0부터 Python 3.9 지원이 제외된다. 0.128.8 패키지 메타데이터에 Python 3.9 지원이 명시되어 있다. [FastAPI 릴리스 기록](https://fastapi.tiangolo.com/release-notes/), [0.128.8 메타데이터](https://pypi.org/pypi/fastapi/0.128.8/json)

- 백엔드 프로젝트의 런타임 요구를 >=3.9,<3.10으로 선언하고 실제 Python 3.9 환경에서 시험한다.
- FastAPI는 0.128.8을 고정 출발점으로 삼는다. Uvicorn·Starlette·Pydantic v2·multipart·HTTP 시험 도구·문서 파서와 모든 전이 의존성은 Python 3.9 및 대상 OS에서 함께 설치·실행된 조합으로 잠근다.
- Python 3.10 전용 타입 표기·match 문법, 3.11 전용 TaskGroup 등은 사용하지 않는다. 기존 Python 빌드·도구와 재사용 코드도 별도로 호환성 검사한다.
- 단계 1에서 OS별 wheel 확보, 해시 있는 의존성 잠금 파일, 오프라인 설치 시험을 수행한다. 현 단계에서 전체 의존성 조합의 설치 성공을 주장하지 않는다.
- Python 3.9는 2025-10-31에 공식 지원이 종료되었다. 사용자 지정 3.9 조건을 유지하되, 배포판의 실제 패치 버전·공급원과 호환 패키지 목록을 기록한다. 이 제한을 이유로 임의로 다른 Python 버전으로 바꾸지 않는다. [Python 공식 일정](https://peps.python.org/pep-0596/)

## 5. API 계약 초안

공통 응답에는 api_version, request_id와 필요한 revision 정보를 둔다. 실패 응답은 code, 사용자 표시 message, retryable을 포함한다. 아래 경로는 단계 1에서 OpenAPI 모델로 고정한다.

| API | 기능·핵심 조건 |
|---|---|
| GET /api/v1/health, /capabilities | 준비 상태, Python·엔진·지식·DB 버전, 파일 형식 지원 상태 |
| /api/v1/auth, GET /api/v1/me | 로그인·로그아웃·세션·권한 있는 사용자 정보. 상세 capabilities는 인증 후 제공 |
| GET /api/v1/catalog | 기존 체크리스트·분류·문구·판정 정책의 표시 데이터. 프론트가 정책을 실행하지 않음 |
| POST /api/v1/documents | 본문·별첨 파일 업로드, 원본 해시·저장 ID 부여 |
| POST /api/v1/reviews | 텍스트 입력 또는 document_id로 검토 생성 |
| GET/PATCH /api/v1/reviews/{id} | 현재 입력·선택·범위와 revision 조회·갱신 |
| POST /api/v1/reviews/{id}/analyses | 202와 job_id 반환. 입력·지식·자료·엔진 버전을 고정한 분석 작업 |
| GET /api/v1/jobs/{id}, /jobs/{id}/result | 진행 단계·결과·실패 사유. 초기 구현은 폴링 |
| POST /api/v1/jobs/{id}/cancel | 취소 요청. 완료·취소 경합에서도 오래된 결과를 반영하지 않음 |
| PATCH /api/v1/reviews/{id}/items/{check_id} | 수기 판정·의견·조항 연결. revision 충돌은 409, 재지정은 해당 항목 중심 재평가 |
| PUT /api/v1/reviews/{id}/draft | 계약별 초안 자동저장. UI 커서·선택영역은 프론트가 유지 |
| POST /api/v1/reviews/{id}/complete | 현재 미판정 수를 서버에서 재확인하고 저장을 하나의 논리적 단위로 완료 |
| POST /api/v1/reviews/{id}/exports | 현재 의견·판정 revision에 해당하는 기존 형식 내보내기 |
| POST /api/v1/reference-searches | 핵심 분석과 분리한 참고 검색 작업. 미조회와 결과 없음 구별 |
| /api/v1/knowledge, /history, /templates | 기존 지식·이력·표준 등록, 검색, 갱신, 백업·복원 |

| /api/v1/backups | DB·파일·manifest를 포함한 검증 가능한 백업·복원 |

분석 결과는 clauses, 선택 체크·적용범위, 후보·점수·순서, 본문/별첨 근거 위치, 판정·사유·자동근거, 수기 재확인 상태, 3열 표시 위치, 완료 집계를 포함한다. 초기 어댑터는 기존 core·subCoverage 등 결과 형태를 유지해 화면 변경을 줄인다. 최종 API 계약에서는 각 필드의 타입·정렬 규칙·빈 값 의미를 명시한다.

## 6. 분석 작업·버전·취소

- CPU 중심 분석을 async 라우트 안에서 직접 돌리지 않는다. API 수신과 분석 프로세스를 분리한다. [FastAPI 동시성 안내](https://fastapi.tiangolo.com/async/)
- 작업 상태는 queued → running → completed / failed / cancelled / interrupted로 저장한다. 초기에는 분석 동시 실행 수를 제한한다.
- 각 작업은 input_revision, source_revision, knowledge_version, engine_version을 캡처한다. 결과 저장 직전에 현재 값과 대조하고, 불일치 시 기존 수기 결과를 덮지 않는다.
- Python 3.9의 실행 중 Future.cancel만으로 강제 중지가 된다고 가정하지 않는다. 단계 사이 협력 취소를 구현하고, 응답하지 않는 작업은 유예시간 후 감독 프로세스가 종료한다. 작업 프로세스는 최종 DB 저장을 직접 하지 않는다.
- 서버 재시작 시 실행 중 작업을 interrupted로 표시한다. 사용자가 확인 가능한 상태에서 재시도하며, 동일 요청은 idempotency_key로 중복 완료를 막는다.
- 초기 배포는 Uvicorn API 프로세스 1개를 기본으로 하고 CPU 분석은 별도 작업 프로세스로 분리한다. 공유 상태는 서버 한 곳의 SQLite에 둔다. 짧은 BEGIN IMMEDIATE 트랜잭션과 busy_timeout으로 쓰기를 직렬화하고, DB 연결을 프로세스 사이에 전달하지 않는다. 작업을 트랜잭션으로 선점하고 lease·heartbeat·소유 작업자 ID로 중복 실행과 고아 작업을 식별한다. 재실행 가능성과 결과의 한 번만 적용을 구별하며, 완료 반영은 멱등하게 한다.
- 요청자·계약 접근범위를 작업에 기록한다. 실행·진행 조회·취소·결과 다운로드마다 권한을 확인한다. 참고 검색 캐시는 사용자 권한 범위와 자료 버전을 키에 포함하여 다른 계약의 근거가 새지 않게 한다.
- 전체 자료를 매번 브라우저에서 전송하지 않는다. API에는 자료 ID·버전을 전달하고, 서버에서 버전 있는 자료와 검색 색인을 재사용한다.
- 문서·참고자료 변경 시 관련 색인을 갱신한다. 편집과 참고 검색은 핵심 분석 전체를 다시 실행하지 않는다.

## 7. 저장·자료 이관

운영 DB 개발 기준은 서버 로컬 SQLite이다. 팀원 PC는 API를 통해서만 접근한다. DB 파일을 공유폴더/NFS/SMB에 두거나 여러 서버에서 직접 열지 않는다. 동시 사용자는 10명 이하이며, WAL·짧은 쓰기 트랜잭션·잠금 제한시간·409 편집 충돌을 구현하고 실제 동시 요청을 시험한다. [SQLite 공식 사용 지침](https://www.sqlite.org/whentouse.html)

원문은 서버 전용 저장소에 두고 코드 저장소와 분리한다. 연결은 요청/작업별로 열고 닫으며 SQLite 표준 라이브러리의 온라인 백업 API와 원문 manifest를 동일 복구 기준으로 묶는다. 실행 중 DB 파일만 단순 복사하지 않는다. 업데이트 전 백업과 정기 백업을 구현한다. 초기 RPO 목표는 24시간, RTO 목표는 4시간으로 두고 사내 운영 기준에 맞춰 확정한다. 복원 시험은 별도 DB·파일 경로에서 수행한다. 쓰기 대기·작업량이 수용 기준을 넘으면 저장소 어댑터를 유지한 채 서버형 DB를 별도 검토한다.

논리 테이블: schema_migrations, users, teams, sessions, review_memberships, documents, document_versions, reviews, review_inputs, review_items, opinion_drafts, source_documents, source_acl, templates, corpus_entries, evaluation_runs, jobs, job_events, audit_events, settings, migration_runs. 검색 색인은 재생성 가능한 파생 데이터이며 원본·수기 의견과 구별한다. 초안은 검토·사용자 단위로 격리하고, 최종 의견은 revision을 가진 공동 검토 기록으로 저장한다.

완료 저장은 판정·최종 의견·아카이브 메타데이터·코퍼스 변경을 같은 DB 트랜잭션에 넣는다. 원문 파일은 먼저 임시 저장·해시 검증·원자적 이름 변경을 완료하고 DB가 참조한다. 파일시스템과 DB에 걸친 단일 트랜잭션을 주장하지 않는다. 중단 시 미참조 파일 정리·누락 참조 탐지로 복구한다. 원문 저장 실패를 정상 완료로 표시하지 않는다.

이관 대상은 지식팩·이력팩만이 아니다. 아래 목록 전체를 inventory로 고정한다.

- 지식 cr-legal-opinion-knowledge-v1, 이력 cr-review-history-pack-v1 및 기존 XLSX 입력 형식.
- 코퍼스 cr-loop-corpus-v2, 개별 검토 판정·수기 의견·근거 연결·검토자·적용범위·별첨 사용 상태.
- 표준 라이브러리·표준 연결·표준 자동평가 패킷, 평가·안전성 작업대 자료와 이력.
- 모든 기존 localStorage 키와 IndexedDB 데이터베이스·스토어. 브라우저 표시 설정은 별도로 구분.

새 앱은 구 file/실행기 origin의 저장소를 직접 읽을 수 없다. 기존 실행기와 같은 origin에서 작동하는 내보내기 보조 기능으로 migration bundle을 만든 뒤 새 앱에 가져온다. 보조 기능은 기존 배포본 복사본에서 시험하며, 필요하면 이관용 별도 업데이트로 제공한다. 브라우저 프로필 DB를 직접 읽거나 사용자 저장소를 자동 삭제하지 않는다.

bundle에는 형식 버전·원본 앱 버전·파일별 해시·스토어별 건수·누락 목록을 포함한다. import preview → 임시 저장·검증 → DB 적용 → 건수·관계·원문 해시 비교 순서를 지킨다. 같은 bundle을 다시 넣어도 중복되지 않으며, ID 충돌·손상 파일은 묵살하지 않는다. 수기 의견과 알 수 없는 구버전 필드는 보존한다.

개인별 이관 자료에는 원본 사용자·이관자·귀속 팀·접근범위를 명시한다. 이관한다고 모든 팀원에게 자동 공개하지 않는다. 동일 내용 해시라도 다른 사용자의 권한·수기 의견은 합치지 않는다. 공용 표준·지식 승격은 관리 권한으로 수행하고 기록한다.

기존 contract_hash는 legacy 식별자로 보관하고 새 document_id에 매핑한다. JS 문자열 UTF-16 처리·정규화·정렬·정수 해시와 Python 동작 차이를 검사한다. 자동판정의 과거 증적은 원형 보존하되 새 엔진 유효 결과와 분리하고, 새 엔진으로 재평가한 결과만 현재 자동판정으로 사용한다. 수기 판정은 기존 의존성·재확인 정책에 따라 보존한다.

롤백은 v1.90.8 배포본과 이관 전 원본 백업으로 가능하게 한다. 전환 후 새 작업은 백업과 지원되는 구형 교환 형식으로 내보낸다. 구버전이 표현할 수 없는 신규 필드는 차이를 안내하며, 완전한 역이관을 검증 없이 보장하지 않는다.

## 8. 공용 서버 인증·권한·배포

- 외부 인터넷 요청 0건을 유지한다. 사내 브라우저↔웹/API·DB·승인된 내부 인증·선택형 모델 서버 통신은 허용 목록으로 구별해 시험한다.
- 사내 HTTPS 주소로 서비스한다. API는 웹서버 뒤의 loopback 또는 허용된 서버망에만 바인딩하고, 프록시 전달 헤더는 신뢰하는 프록시에서만 받는다. 운영은 동일 origin을 기본으로 하며, 개발 CORS는 실제 프론트 origin만 허용한다. [FastAPI CORS 안내](https://fastapi.tiangolo.com/tutorial/cors/)
- 인증은 관리자가 발급하는 앱 계정으로 먼저 구현한다. SSO는 회사 계정 통합 로그인이며 현재 제공 여부는 미확인이다. 추후 필요할 때 별도 인증 어댑터로 연결한다. 인증 어댑터를 분리하며 익명 운영·개방 회원가입은 하지 않는다. 앱 계정은 검증된 비밀번호 해싱·시도 제한·세션 만료를 적용한다. 세션은 HttpOnly·Secure·SameSite 쿠키와 서버 저장소로 관리하고 쓰기 요청은 CSRF 검증을 한다.
- 역할 기본안은 운영관리자·지식관리자·검토자·조회자이다. 역할과 계약별 담당/공유 대상을 함께 검사한다. 운영관리자에게 계약 원문 접근을 자동 부여하지 않는다. 요청 ID·문서 ID를 바꿔도 권한 밖 원문·의견·검색·작업 결과를 받을 수 없게 한다.
- 기존 자유입력 검토자 이름은 이관 이력으로 보존하고 새 작성자는 인증 계정에 연결한다. 동일 계약 동시 편집은 revision 충돌로 알리고 덮어쓰지 않는다. 실시간 공동 편집은 구현하지 않는다.
- 로그인·원문 열람/다운로드·판정 저장·공유범위 변경·표준/지식 변경·이관·백업·복원을 감사 이벤트로 기록한다. 로그에는 원문·의견 전문·자격정보를 남기지 않는다. 업무 원문·판정 이력은 권한 있는 DB 기록으로 보관한다.
- 업로드 크기·압축 해제 크기·파일 개수·경로 이탈·파서 시간제한을 검사한다. 계약 원문이나 토큰을 오류 로그에 남기지 않는다.
- 문서 파서·정적 파일·API 문서 자원도 로컬에서 제공한다. 기본 Swagger CDN 의존은 제거하거나 배포판에서 문서 UI를 비활성화한다.
- 서버 서비스 설치·업데이트·백업·복원의 데이터 경로를 고정한다. 코드 배포로 운영 DB를 덮어쓰지 않는다. 클라이언트에는 Python이나 실행기를 설치하지 않는다.
- 기존 .crupdate는 브라우저 앱용이다. Python 앱 업데이트에 재사용하지 않고 프론트/API/DB 버전이 함께 명시된 배포 패키지를 만든다.
- 확정된 서버 OS에서 Python 3.9 실제 실행·오프라인 설치·자동 재시작·프록시·인증·업데이트·복원까지 통과해야 배포 가능 상태로 판단한다. Windows 팀원 PC의 사내 브라우저 접속도 검증한다. 개발 PC 시험만으로 대체하지 않는다.

## 9. 완료 정의

1. 실제 Python 3.9에서 FastAPI·분석·저장·파일 처리·시험이 동작한다.
2. 프론트와 백엔드가 별도 빌드·실행되며, 기존 UI 동선이 유지된다.
3. 핵심 분석·판정·검색·평가가 Python에서 실행되고, 배포 런타임에 Node/JS 엔진 호출이 없다.
4. 기본 엔진 비교군에서 체크·매핑·판정·근거·출처·표시 순서·수기 보존·완료 조건의 설명되지 않은 차이가 0건이다.
5. 기존 기능 대응표의 모든 항목이 구현·검증 상태이며, 누락된 관리 화면이나 파일 형식이 없다.
6. 저장·재시작·초안 복구·이관·중복 입력·실패 복구·백업 복원의 무결성을 검증한다.
7. 외부 인터넷 요청 0건과 대상 서버 환경의 설치·실행 및 팀원 브라우저 접속을 검증한다.
8. 사용자·계약별 권한, 자료 이관 귀속, 동시 편집 충돌, 검색·작업 격리, 감사 이력과 서버 백업·복원을 검증한다.
