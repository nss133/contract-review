- [ ] 목표 게이트: 같은 장비의 분석 중앙값은 기준판 대비 20% 이상 악화하지 않고, 편집·저장 UI 대기는 200ms 이내를 목표로 한다. 측정 결과로 충족 여부를 판단하며 사전 보장하지 않는다.
- [ ] 부분 재지정에서 전체 매핑 재실행 0회, 참고 검색 분리, 브라우저 긴 정지 감소를 확인한다. 정확도와 수기 보존은 성능보다 우선한다.
- [ ] 프론트 API 실패·409 충돌·재시도·초안 보존·인쇄·실제 파일 내보내기를 전체 흐름으로 확인한다.
- [ ] 초기 부하 시나리오는 5명·10명 동시 접속으로 두고, S0의 실제 팀 규모에 맞춰 조정한다. 동시에 분석·검색·의견 저장할 때 응답시간·메모리·DB 대기·작업 공정성을 측정한다. 단일 사용자 기준을 다중 사용자 성능 보장으로 쓰지 않는다.

통과 기준: 정확성·자료 보존 게이트 통과, 성능 수치와 남은 차이 공개, 사용자 화면에서 구현상 세부정보가 불필요하게 노출되지 않음. 로컬 측정을 폐쇄망 실장비 성능으로 표현하지 않는다.

## S8. 오프라인 배포·전환·복구

산출물: frontend 정적 패키지, backend Python 3.9 패키지와 wheelhouse, 서버 서비스·역방향 프록시 설정, 설치·업데이트·이관·복구 안내.

- [ ] 대상 서버 OS·아키텍처·Python 3.9 패치·SQLite·웹서버·관리자 발급 계정·팀원 브라우저·실행 정책을 실제 환경에서 확인한다.
- [ ] 인터넷 차단 환경에서 의존성 설치·앱 시작·health 준비·브라우저 연결을 검증한다. 실행 중 외부 다운로드와 CDN을 제거한다.
- [ ] 프론트·API 버전 불일치, 포트 점유, DB 버전 불일치, 원문 디렉터리 권한·공간 부족을 처리한다.
- [ ] 릴리스 manifest에 프론트/API/엔진/지식/DB 버전·해시·런타임 요구를 기록한다.
- [ ] 앱 업데이트 후 사용자 자료 보존, 이관 후 검토 재개, 백업 복원과 구버전 복귀를 실제 파일로 검증한다.
- [ ] Node나 브라우저 Worker의 기존 판정 엔진 없이 주요 기능 전체가 실행되는지 확인한다.
- [ ] 사내 HTTPS 주소에서 여러 계정으로 접속하고 계약별 권한·검색 격리·동시 수정 충돌·감사 이력을 검증한다. 서비스 자동 재시작·DB 복구·원문 복원 및 인증서 신뢰도 확인한다.
- [ ] 기능 대응표·시험 결과·미해결 제한을 배포 기록에 첨부한다. 모든 완료 정의를 충족한 경우에만 전환 완료로 표시한다.

통과 기준: Python 3.9·FastAPI·프론트/백엔드 독립 실행·UI 보존·기능 동등성·자료 이관·공용 서버 인증/권한·동시 사용자·대상 OS 배포를 모두 확인. 기존 ZIP은 복구 기준으로 보존한다.

## 첫 구현 범위

다음 실제 구현은 S0와 S1부터 시작한다. 먼저 동등성 픽스처·저장소 inventory·Python 3.9 설치 및 의존성 잠금·API 골격을 만든다. 새 규칙·새 UI·팀 협업 기능은 이 초기 작업에 섞지 않는다.

일정은 S0에서 기능 목록을 고정하고 S4의 HWP/DOC/PDF 파서와 태그 엔진 표본 포팅 난도를 확인한 후 산정한다. 단순 API 포장만으로 전체 전환 일정을 추정하지 않는다.
