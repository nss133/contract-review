# 구조화 태그 매칭 운영설계

## 목적

문자열 유사도만으로는 “같은 단어가 등장함”과 “같은 법률요건을 충족함”을 구별하기 어렵다.
구조화 태그층은 계약 조항과 체크항목을 같은 축으로 변환하여 후보의 의미적 연결성을 설명하고,
검증된 범위에서만 재정렬 신호로 사용한다. 최종 판정은 계속 사람에게 있다.

## 데이터 흐름

1. `legal-opinion-tagger/lib/contract-tag-profile.mjs`가 조항 전체 집계와 별도로 항·문장 단위 명제 프레임에서 주제·주체·행위·대상·규범강도·조건을 추출한다.
2. `scripts/build-contract-bridge.mjs`가 브라우저 IIFE, Node CJS, taxonomy JSON을 만들고 생산 패키지 버전과 SHA-256 manifest를 기록한다.
3. `build/sync_contract_tags.py`가 세 산출물의 manifest 해시를 검증한 뒤 `vendor/`에 동기화한다.
4. `knowledge/tag_taxonomy.yaml`은 태그 정본, `knowledge/tag_signatures.yaml`은 체크별 요구 태그를 관리한다.
5. `src/contract_tags.js`가 같은 명제 프레임 안의 관찰 태그와 체크 요구 태그를 비교해 일치·누락·충돌·근거 문장을 반환한다.
6. `src/matcher.js`는 모드에 따라 trace만 남기거나 제한된 보조점수를 적용하고, `assessment.js`가 이를 별도 원장에 기록한다.

## 개인정보 관계 태그 게이트

개인정보 문서에는 단순 유사도보다 먼저 `처리위탁 / 독립적 제3자 제공 / 혼합 / 불명확` 관계 태그를
부여한다. 문장별로 개인정보 주제, 제공 행위, 금지·동의 규범강도를 함께 읽고 다음처럼 처리한다.

- `제3자에게 제공하여서는 아니 된다`는 `third_party_provision_prohibited`로 기록하고 실제 제공 신호에서는 제외한다.
- `위탁업무·수탁자·처리위탁`은 `processing_outsourcing` 관계의 근거가 된다.
- `제공받는 자·그 이용목적·제3자 제공 동의`는 `third_party_provision`의 강한 근거가 된다.
- 두 구조가 함께 있으면 `mixed`로 두어 두 증빙 경로를 모두 유지한다.

체크의 `relationship_scope`와 문서 관계가 다르면 조항별 유사도 계산 전에 종료한다. 이 때문에
처리위탁 약정서에서 제3자 제공 동의·법정고지 카드가 번지는 오탐을 줄이는 동시에, 불필요한
체크×조항 점수계산도 생략한다. 제3자 제공이 실제로 확인되면 `implementation_channel`에 따라
계약 문구가 아니라 동의서·개인정보 처리방침·고지화면 등 외부 증빙을 확인하도록 안내한다.

## 모드와 안전장치

| 모드 | 동작 | 용도 |
|---|---|---|
| `off` | 태그 분석을 하지 않음 | 장애 격리·비교 기준 |
| `shadow` | 분석·기록만 하고 기존 점수는 0점 조정 | 비교 기준·정확도 측정 |
| `assist` | 검수된 signature에 한해 +18/-12점 이내 보조 | 배포 기본값(검수 16개 한정) |

- `candidate`는 자동 생성 후보이고 매칭 점수에 쓰지 않는다.
- `curated`만 사람이 축·필수조건을 확인한 정본으로 사용한다.
- 필수 축이 하나라도 누락되면 부분 일치 가점을 주지 않는다.
- 필수 축은 같은 항·문장 프레임 안에서 함께 충족되어야 한다. 서로 다른 문장의 태그를 합산해 가점하지 않는다.
- 조 제목은 바로 아래 항·문장의 쟁점 문맥으로만 공급하고, 제목 자체를 독립 충족 문장으로 보지 않는다.
- `금지` 요구와 `무조건 허용` 관찰처럼 규범강도가 충돌하면 제한 감점한다.
- 태그만으로 체크를 새로 노출하거나 `이상없음`을 자동 기재하지 않는다.

## 초기 적용범위와 확장

현재 240개 전체 체크의 후보를 생성할 수 있고, 오부착 비용이 큰 공통·개인정보·정보보안·NDA의
16개 체크만 `curated`로 실제 보조점수에 사용한다. 후보 생성은 `python3 build/generate_tag_signatures.py`로
하되 정본을 자동 덮어쓰지 않는다. 신규 signature는 대표 양성·혼동 음성 문장을 함께 검수하고,
기존 골드셋과 `shadow↔assist` 비교가 모두 통과한 뒤 승격한다.

## 사람 승인형 누적 개선

1. 검토자가 자동 연결 조항을 확인하거나 다른 조항으로 재지정한다.
2. 반출 데이터에는 계약 원문 대신 정답 조항과 오답 Top1 조항의 구조태그만 저장한다.
3. 체크별 표본 5건 이상, 동일 태그 지지율 80% 이상일 때만 개선 후보를 만든다.
4. 리포트의 `팀·지식 관리 > 구조태그 개선 후보`에서 사람이 승인하거나 보류한다.
5. 승인안은 JSON으로 반출하고 다음 배포의 `shadow`·`assist` 골드셋을 모두 통과한 뒤 정본에 반영한다.

사람 승인은 즉시 로컬 매칭 규칙을 바꾸지 않는다. 표본 편향이나 잘못된 단건 교정이 전체 시스템을
오염시키지 않도록 승인과 배포 회귀검증을 분리한다.

## 화면과 감사추적

체크 카드의 “구조태그” 상세 영역에서 같은 항·문장 확인 여부, 판정 근거 문장, 한글화된 일치 요소,
같은 문장에서 확인되지 않은 요소와 충돌을 확인할 수 있다. 조항 전체 태그 합계는 감사·진단용으로
남지만 assist 가점에는 사용하지 않는다.
한 조항에 카드가 4건 이상 몰리면 첫 주제 태그별로 시각적 묶음을 만들되 카드를 숨기거나 판정을
합치지 않는다. 내보낸 시스템 평가에는 프로필 버전, 원점수, 실제 보정점수, 관찰 태그와 근거가
`tag_analysis`로 분리되어 재현성과 사후 분석을 지원한다. 평가 원장 상단에는 태그 생산 패키지 버전,
엔진·taxonomy 해시를 함께 남겨 어느 태거 산출물로 판정했는지 재현할 수 있다.
