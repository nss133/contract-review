# 폐쇄망 계약검토 이력 데이터 계약 v1

## 목적

계약검토 이력 XLSX를 폐쇄망 브라우저에서만 읽고, 신청값·검토결과값·시스템 추론·사람 판정을 섞지 않고 보존하기 위한 입력 규격이다. 실제 행과 백업 파일은 폐쇄망 밖으로 반출하지 않는다.

## 지원 입력

- 워크시트: 계약서 검토를 우선 사용하며, 없으면 첫 워크시트를 검사함
- 머리글: 상단 15행 안에서 33개 표준 열 중 24개 이상이 정해진 위치와 일치해야 함
- 범위행: A열 범위, B열 완료 또는 ALL 반복행은 데이터에서 제외함
- 데이터행: 완전히 빈 행만 제외함. 완료 외 상태도 원문 그대로 보존함

## 33개 표준 열

| 열 | 내부 필드 | 발생시점 |
|---:|---|---|
| B | status | 현황 |
| C:R | request.* | 신청 |
| S:AG | result.* | 검토 완료 |

신청과 결과에 반복되는 작성자·작성일·부서·신청자·보안등급·계약명·개인정보/업무위탁 여부·계약기간·유형·신규/변경/연장은 서로 덮어쓰지 않는다. 값이 다르면 REQUEST_RESULT_CONFLICT 진단을 남긴다.

## 안정적 식별자

표준 33열 밖에 다음 머리글 중 하나가 있으면 원천 검토번호로 사용한다.

- 계약검토ID
- 계약검토번호
- 검토ID
- 검토번호
- 접수번호
- 문서ID
- review_id

원천 식별자가 없으면 신청·결과의 일부 메타데이터로 LOCAL 임시 ID를 만든다. 임시 ID는 동일 계약군 확정이나 원천시스템의 영구 식별자를 대체하지 않는다.

## 표준 진단코드

| 코드 | 의미 |
|---|---|
| SCHEMA_HEADER_MISMATCH | 33열 머리글 구조를 안전하게 인식하지 못함 |
| STABLE_ID_MISSING | 원천 검토번호가 없어 임시 ID를 사용함 |
| PROVISIONAL_ID_COLLISION | 같은 임시 ID 후보가 한 파일 안에서 중복됨 |
| CONTRACT_NAME_MISSING | 신청·결과 모두 계약명이 없음 |
| REQUEST_RESULT_CONFLICT | 신청값과 결과값 중 하나 이상이 다름 |
| REQUEST_DATE_PARSE_FAIL | 신청 작성일 표기를 날짜로 해석하지 못함 |
| RESULT_DATE_PARSE_FAIL | 결과 작성일 표기를 날짜로 해석하지 못함 |

## 저장·업데이트

- IndexedDB 이름: contract-review-history
- 이력팩 형식: cr-review-history-pack-v1
- 동일 review_id와 동일 내용지문은 중복 집계하지 않음
- 동일 review_id의 내용이 달라지면 이전본을 지우지 않고 리비전으로 보존함
- DB 유형 연결 설정과 내부 벤치마크는 앱 버전과 독립해 보존함
- crupdate에는 실제 이력·설정·라벨·평가결과를 포함하지 않음
- crhistory 백업은 실제 검토정보를 포함하므로 폐쇄망 내부에서만 보관함

## 법적 판단과의 경계

- 과거 DB 유형은 현재 유형의 참고 후보임
- 개인정보/업무위탁 기재값은 당시 신청·검토 기재이며 현재 적용범위의 증거가 아님
- 검토결과 자유서술은 쟁점 후보이며 조항 연결이나 수정 필요의 정답이 아님
- 현재 계약의 유형·적용범위·체크항목·최종조치는 계속 검토자가 확인함
