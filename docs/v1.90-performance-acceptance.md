# v1.90 멈춤 재발 방지 수용시험

## 범위와 입력

[시험 스크립트](../build/test_v190_performance.mjs)는 저장된 v1.89.0 업데이트와 새 v1.90 HTML을 동일한 합성 자료로 실행한다. CPU 1배·4배 각각 이전/신규 버전 1쌍을 비교한다. 실제 `분석 시작` 버튼을 누르고 종료 상태를 기다린다. 분석 함수를 동기 호출해서 끝난 것으로 간주하거나, 가짜 매핑·자동판정·캐시를 주입하지 않는다.

재현 입력은 이전 멈춤 진단과 같은 본문 2,821자, 조문 본문 14종×4회, 태깅 문서 500건, 문서당 고유 근거 52문장(총 26,000문장), 합성 코퍼스 29건이다. 근거 문장은 약정 관련 기본 문구 7종에 문서별 고유 내용을 붙여 문자열이 모두 다르다. 의미적으로 독립된 26,000개 쟁점이라는 뜻은 아니다. 태그 정의는 14개이며, 문서당 태그 연결 52개와 실제 파일의 52개 태그 칼럼은 구분한다. 실제 계약·태깅 원본·사용자 코퍼스는 읽지 않는다.

브라우저는 전용 프로필과 별도 BrowserContext를 사용한다. 시험 페이지와 Worker의 외부 HTTP/WebSocket 요청을 차단하고 호출 여부를 기록한다. 이전 업데이트의 내장 SHA-256, 실제 앱 버전, 엔진 버전, 실행한 HTML 해시를 확인한다. 구 v1.89 시험 파일과 배포물을 수정하지 않는다.

## 독립 합격 조건

| 점검 | 기준 |
|---|---|
| 실제 버튼 경로 | 완료 이벤트/상태 확인, 성공 시 분석 버튼 복구 |
| 응답성 | CPU 4배 지연 조건에서 25ms heartbeat 지속, 최대 heartbeat 간격 및 LongTask 각각 1,000ms 미만 |
| 분석 결과 | 이전 버전과 체크 ID, best/ranked/coverage, 자동판정 ID·reason, proof 원문 좌표 및 조항 배치가 동일 |
| 취소 | 실제 Worker 실행 중 및 Worker 완료 후 자동판정 검증 중 각각 취소, 1,000ms 미만에 종료, 부분 결과·수기 저장소·Archive 미커밋 |
| 입력 변경 | Worker 실행 중 본문을 바꾸면 이전 입력 결과를 저장하지 않고 취소 |
| Worker 불가 | 생성자를 실패시키는 환경 주입 시 명확한 오류·버튼 복구·spinner 종료; 무제한 대기나 동기 분석 fallback 금지 |
| 수기 보존 | 실제 메모 input 직후 페이지 새로고침 및 재분석에서 마지막 입력·수기 출처 유지 |
| 지연 생성 목록 | 미접근 드롭다운에 전체 조항을 미리 넣지 않고, 실제 focus/pointerdown 시 해당 목록만 확장 |
| 별첨 근거 | 별첨 12개 근거를 proof에 유지하면서 완료 카드의 원문 인용·근거 버튼은 각각 0~1개, 팝업의 실제 인용 좌표 확인 |

매 조건의 총시간과 최대 멈춤 시간을 원시 자료로 기록한다. 최초/단일 실행은 P50/P95로 표현하지 않는다. `Worker.postMessage`는 플랫폼 메서드를 원래 인수와 반환값 그대로 호출하면서 동기 복제 시간을 계측한다. Worker의 CPU 지연 적용 여부는 별도로 기록하며, 페이지 CPU 4배가 모든 Worker에 적용된 것처럼 표기하지 않는다. DOM 단계 시간은 런타임 완료 이벤트가 제공하는 단계 계측값과 구분하여 기록한다.

실패 로그는 미처리 예외, console error, Worker 초기화/네트워크 격리 오류, 진행 단계와 완료 오류를 구분한다. 분석 완료 제한은 60초다. timeout은 성공이나 일반적인 보류로 처리하지 않는다.

## 최종 빌드 결과

[원시 결과 JSON](v1.90-performance-acceptance.json)의 10개 조건이 모두 통과했다. 최종 HTML SHA-256은 `a30d69c8efa8c848766e9a9e66916a3eca169dedf8c354ad11d8ae1b34c260ba`, 이전 배포본은 `26ae13ef4e9ddf6c0fd650b2f27cf5dc5475dc661b49d1e816ff9c4c6923c962`다. Chrome 153.0.8010.48에서 다른 CPU 회귀 작업과 분리하여 실행했다.

아래는 조건마다 한 번 측정한 `v1.89 → v1.90` 값이며 단위는 ms다. P50/P95 또는 개선률 보증이 아니다.

| 페이지 CPU 조건 | 버튼 클릭~분석 완료 | 최대 heartbeat 간격 | 최대 LongTask |
|---|---:|---:|---:|
| 1배 | 6801.8 → 4025.9 | 5003.4 → 85.9 | 4992 → 84 |
| 4배 | 21100.5 → 4577.6 | 19193.8 → 334.2 | 19156 → 326 |

CPU 1배/4배 모두 활성 체크 28개·자동판정 13개가 같고, 전체 best/ranked/coverage·자동판정 reason·proof의 원문 좌표·조항 배치가 전후 일치했다. 이 합성 입력의 판정 수를 실제 계약 자동판정률·정확도로 일반화하지 않는다.

Worker 직접 CPU 지연 설정 요청은 `Operation is only supported for pages, not workers`로 거부됐다. 따라서 4배 조건은 주스레드 설정/Worker 기본 실행으로 구분하며 전체 장치가 4배 느려진 결과로 표현하지 않는다. 현재 버전의 데이터 전달 복제 시간은 CPU1 7.2ms/CPU4 29.3ms, 런타임이 기록한 화면 렌더 구간은 41.8ms/68.6ms였다. Worker 왕복 구간은 3743.6ms/3918.2ms로, 전달·대기와 일부 겹칠 수 있으므로 각 단계 값을 단순 합산하지 않는다.

실제 Worker 실행 중 취소는 0.9ms, 본문 변경에 따른 취소는 5.4ms, Worker 완료 후 자동판정 검증 중 취소는 0.8ms였다. 세 경우 모두 부분 결과·판정 저장·Archive 저장이 발생하지 않았다. Worker 생성 불가 환경은 281.1ms에 명시 오류로 종료하고 spinner와 버튼 상태를 복구했다. 수기 마지막 입력의 실제 새로고침/재분석 보존, 선택목록 1개만 5→59 옵션으로 지연 확장, 별첨 proof 12개 유지·근거 버튼 1개·inline 인용 0개·정확한 원문 팝업도 통과했다.

## 실행

최종 HTML 빌드 후 전용 CDP를 준비하고, 다른 성능 측정·대규모 회귀 작업과 겹치지 않게 실행한다.

```sh
CR_TEST_ENDPOINT=http://127.0.0.1:9372 CR_OUTPUT=docs/v1.90-performance-acceptance.json node build/test_v190_performance.mjs
```

결과는 위 JSON의 HTML 해시와 함께 확정하며, 실제 폐쇄망 장비 속도나 법적 정확도 일반화에 사용하지 않는다.
