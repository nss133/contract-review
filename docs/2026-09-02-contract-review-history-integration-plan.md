## 1. 결론

기존 개선안의 큰 방향은 타당하다. 특히 태깅은 `legal-opinion-tagger`, 계약유형·적용범위·체크리스트·사람 판정·과거 검토 재사용은 `contract-review`가 담당한다는 프로젝트 분리, DB 기재값과 시스템 판단 및 사람의 최종판정을 분리한다는 원칙은 유지해야 한다.

다만 운영 전제를 다음과 같이 바로잡는다.

> 실제 계약검토 데이터·계약명·상대방·작성자·검토결과·첨부·태깅 근거는 폐쇄망 밖으로 반출하지 않는다. 외부 개발환경에서 실제 약 2천 건을 직접 프로파일링하거나 학습하지 않는다. 분석 코드와 빈 스키마, 합성 시험자료만 폐쇄망 안으로 반입하고 실제 데이터 점검·골드셋 구축·성능평가·보조기능 승격은 전부 폐쇄망 안에서 실행한다.

현재 XLSX는 실제 데이터가 아니라 33개 열의 산출요청 양식이므로 외부에서는 열 구조만 확인할 수 있다. 값 분포·중복·누락·첨부 연결상태와 의미 정확도는 폐쇄망용 진단기능이 현장에서 계산해야 한다.

도입 순서는 다음과 같이 조정한다.

1. 외부에서 데이터 비의존 스키마·진단기·합성 회귀시험 준비
2. 폐쇄망에서 실제 데이터 계약 확인과 현장 품질진단
3. 앱 코드와 분리된 계약검토 이력 저장소 구축
4. 저위험 편의기능과 과거 검토 검색
5. 폐쇄망 내부 사람 검증 골드셋과 버전별 평가
6. 내부 기준을 통과한 기능만 보조모드로 승격

## 1.1 망 경계별 역할

| 구역 | 허용 작업 | 금지·제한 |
|---|---|---|
| 외부 개발환경 | 빈 33열 양식 분석, 스키마·가져오기·진단·평가 코드 개발, 합성자료 시험, `.crupdate` 제작 | 실제 행·계약명·상대방·검토결과·첨부·태그 근거 열람 및 보관 금지 |
| 폐쇄망 | 실제 XLSX 적재, 값 분포·오류 진단, 태깅자료 결합, 골드셋 작성, 정확도·편의성 평가, assist 승인 | 내부 데이터가 포함된 파일을 외부 반출하지 않음 |
| 외부로 전달 가능한 피드백 | 앱 버전, 스키마 버전, 원문 없는 오류코드, 승인된 집계지표·기능 요청 | 행 단위 값, 자유서술, 고유명, 파일명, 날짜 조합, 근거문장 반출 금지 |

회사 정책상 집계지표도 반출할 수 없다면 외부 개발자는 정확도 수치를 확인하지 않고 범용 개선코드만 제공하며, 폐쇄망 담당자가 내부 승인표에 따라 승격 여부를 결정한다.

## 2. 실제 XLSX 검증 결과

확인한 양식은 한 개 워크시트 `계약서 검토`의 33개 열로 구성된다. 신청과 검토결과가 별도 시트가 아니라 같은 시트의 열 묶음이다.

| 구분 | 열 | 주요 내용 |
|---|---:|---|
| 화면/현황 | A:B | 칼럼명, 진행상태 |
| 신청 정보 | C:R | 작성자·작성일·부서·계약명·개인정보/업무위탁 여부·기간·금액·유형·상대방·신규/변경/연장·요청내용·파일 |
| 검토결과 | S:AG | 작성자·작성일·부서·계약명·개인정보/업무위탁 여부·기간·유형·난이도·검토유형·신규/변경/연장·검토결과·첨부자료 |

양식에는 머리글과 범위행만 있고 실제 계약검토 행은 없다. 이에 따라 현재 확인할 수 없는 사항은 다음과 같다.

- 약 2천 건의 실제 행 수와 완료·취소·반려·중복 비율
- 유형·난이도·검토유형의 실제 값 목록과 시대별 분류 변경
- 날짜·기간·금액의 표기형식과 결측률
- 개인정보/업무위탁 필드의 신청값과 결과값 일치율
- 계약서·관련자료·첨부자료 셀이 파일명, URL, 내부 식별자 중 무엇인지
- 검토결과 자유서술의 길이·구조·조항 연결 가능성

현재 양식에는 `contract_review_id`, `request_id`, `result_id`, `contract_family_id`, `previous_review_id`, `file_id`가 없다. 이 상태에서는 같은 계약의 재검토·연장·변경을 정확하게 잇거나, 동일한 제목의 별개 계약을 구별하거나, 재수집 시 중복을 안전하게 제거할 수 없다.

또한 신청 영역과 결과 영역에 작성자·작성일·신청부서·신청자·보안등급·계약명·개인정보 여부·업무위탁 여부·계약기간·유형·신규/변경/연장이 중복된다. 가져오기 단계에서 단순히 열 이름만 사용하면 뒤 열이 앞 열을 덮어쓸 수 있으므로 `request.*`와 `result.*` 이름공간으로 분리해야 한다.

## 3. 기존 개선안의 채택·보완·유보 사항

### 채택

- 태거와 계약검토 도구의 책임 분리
- 신청 당시 선언값, 검토결과값, 시스템 추론, 사람 최종판정의 분리 저장
- 메타데이터를 계약조항 충족의 증거로 사용하지 않는 원칙
- `unknown`·`conflict`를 정상 상태로 보존하는 방식
- 계약군과 시간 기준의 평가 분리
- 과거 자료는 자동판정이 아니라 검색·후보·shadow부터 시작하는 방식

### 보완

- 현재 양식은 ‘신청 시트/결과 시트’가 아니라 한 시트의 두 열 블록이므로 위치와 그룹을 함께 검증하는 가져오기 규격이 필요하다.
- 결과 영역의 유형·난이도·검토결과는 사후정보다. 신규 계약의 사전 유형판정이나 체크 노출 모델에 입력하면 정답 누설이 발생한다. 각 필드에 `available_at` 단계를 부여해야 한다.
- 검토결과 자유서술에 쟁점이 언급됐다는 사실과 계약서 수정이 필요하다는 판단은 다르다. `issue_mentioned`, `clause_anchor`, `reviewer_verdict`, `final_action`을 분리해 사람 확인 없이 변환하지 않는다.
- 계약명·상대방 유사도만으로 `contract_family_id`를 확정하지 않는다. 정확한 연결키가 없으면 후보만 보여주고 사람이 확정한다.
- 약 2천 건 전체의 원문·첨부를 모든 브라우저에 적재하지 않는다. 메타데이터 목록, 선택한 검토의 구조화 요약, 원문·첨부의 세 계층으로 나눈다.
- 현재 태깅자료는 IndexedDB에 독립 저장되지만, 판정 코퍼스와 아카이브 일부는 `localStorage`를 사용한다. 대량 이력은 별도 IndexedDB와 백업·복구·스키마 마이그레이션이 필요하다.
- 실제 값 목록을 외부에서 하드코딩할 수 없으므로 유형·부서·상태·첨부 역할의 별칭 매핑은 폐쇄망에서 설정하고 앱 버전과 분리해 영구 보존한다.
- 실제 데이터에서 발생한 오류는 원문을 보여주는 방식이 아니라 표준 오류코드와 현장 미리보기로 해결한다. 외부 수정이 필요하면 승인된 오류코드·건수·재현용 합성행만 전달한다.

### 유보

- 계약기간·금액·상대방을 이용한 우선순위 자동결정
- 과거 검토결과에서 체크리스트 판정이나 계약수정 조치를 자동생성
- 유사 사례의 다수결을 현재 사건의 법적 결론으로 승격
- 실제 값과 사람 검증표본 없이 ‘정확도 향상’을 수치로 주장하는 것
- 실제 내부 자료나 내부 골드셋을 외부 개발용 테스트 픽스처·앱 HTML·업데이트 ZIP에 포함하는 것

## 4. 목표 데이터 구조

계약검토 이력은 기존 `cr-legal-opinion-knowledge-v1`과 분리해 `cr-review-history-pack-v1`으로 관리한다.

### 4.1 필수 식별·계보 필드

| 필드 | 용도 |
|---|---|
| `review_id` | 원천시스템에서 변하지 않는 검토 건 식별자 |
| `request_id`, `result_id` | 신청과 결과 레코드 분리 |
| `contract_family_id` | 동일 원계약의 변경·연장·재검토 묶음 |
| `previous_review_id` | 직전 검토와의 명시적 연결 |
| `source_row_id` | 원천 추적과 오류 재현 |
| `submitted_at`, `completed_at` | 시점 분리와 처리시간 측정 |
| `attachment_id`, `attachment_role` | 검토대상 계약서·원계약·별첨·검토결과 파일 구분 |
| `file_hash`, `file_name`, `mime_type`, `file_size` | 중복·변경·파일 무결성 확인 |

식별자가 원천에 없다면 추출 쿼리 또는 시스템 산출 규격에서 추가하는 것이 원칙이다. 임시 해시는 보조 식별자일 뿐 정식 ID를 대체하지 않는다.

### 4.2 정보 발생시점 분리

- 신청 시점: 계약명, 신청 유형, 신청부서, 상대방, 거래구분, 요청내용, 신청자가 체크한 개인정보/업무위탁 여부
- 검토 시점: 계약 원문, 첨부, 시스템 유형·적용범위·체크 후보, 검토자 수정
- 완료 시점: 결과 유형, 난이도, 검토유형, 검토결과, 최종 파일, 실제 처리 결과

사전 추천과 성능평가에는 그 시점에 실제로 알 수 있었던 정보만 사용한다.

### 4.3 저장 계층

- `history_catalog`: 전체 이력의 최소 메타데이터와 검색용 지문
- `history_records`: 선택 적재한 구조화 신청·결과·사람 라벨
- `history_files`: 승인된 경우에만 파일 메타데이터와 로컬 참조를 저장
- `history_imports`: 원본 지문, 스키마 버전, 적재일, 성공·격리·중복 건수
- `history_labels`: 사람이 확정한 유형·적용범위·체크·조항·조치 라벨
- `history_config`: 폐쇄망에서 확정한 열 매핑·코드 별칭·표시 설정
- `history_benchmarks`: 내부 골드셋의 식별자·라벨과 앱 버전별 평가결과

앱 업데이트 파일과 데이터 저장소를 분리하고, 가져오기는 `review_id + revision` 기준의 멱등 upsert로 처리한다. 삭제나 덮어쓰기 없이 새 리비전을 보존한다. `.crupdate`에는 실행코드와 공개 스키마만 포함하고 `history_*` 저장소, 내부 설정, 골드셋, 평가결과를 포함하지 않는다.

현재의 고정 실행기 방식을 유지해 같은 브라우저 origin의 IndexedDB를 계속 사용한다. 업데이트 전에는 폐쇄망 내부에서만 `.crhistory` 백업을 만들고, 스키마 변경은 새 저장소에 복사·검증한 뒤 전환한다. 실패하면 기존 저장소를 그대로 사용해야 하며 재반입을 요구해서는 안 된다.

## 5. 단계별 구현계획

### P0. 외부 개발환경 준비

실제 데이터 없이 다음을 개발한다.

- `docs/history-data-contract.md`와 원천 열 → 내부 필드 매핑 초안
- 33열 구조·2단 머리글·중복 머리글을 인식하는 범용 진단기
- 누락·형식오류·중복·충돌을 표준 코드로 표시하는 품질점검 화면
- 코드값을 사용자가 폐쇄망에서 매핑할 수 있는 설정 UI
- 합성자료와 경계자료로 만든 가져오기·저장·마이그레이션 회귀시험
- 내부 자료가 없는 빈 `.crupdate` 배포물

외부 단계의 완료 기준은 합성자료 처리와 오류 복구가 검증되는 것이다. 실제 데이터의 품질이나 의미 정확도가 확보됐다고 판단하지 않는다.

### P0-I. 폐쇄망 현장 품질진단

폐쇄망 담당자가 실제 XLSX를 진단기에 넣으면 다음 결과가 화면과 폐쇄망 내부 보고서에만 나타난다.

- 행 수, ID 유일성, 완료상태별 건수, 중복·누락률
- 신청/결과 중복 필드의 일치·충돌·미기재 행렬
- 유형·난이도·검토유형·신규/변경/연장 값 분포
- 날짜·금액·기간 파싱률
- 첨부 연결 성공률과 한 건당 파일 수
- 동일 제목·상대방·유사 파일 지문 군집

계약명·상대방·작성자·검토결과 등 행 단위 미리보기는 폐쇄망 화면에서만 확인한다. 저장 가능한 진단보고서도 폐쇄망 내부 전용으로 표시한다.

원천시스템에 안정적 `review_id`와 첨부 연결키가 있으면 매핑한다. 없다면 폐쇄망 내부에서 임시 로컬키를 만들 수 있으나, 계약군 자동확정과 재적재 멱등성의 한계를 명시한다. 이 경우 원천 산출규격 보완을 우선한다.

### P1. 이력팩 가져오기와 영구 저장

구현 후보:

- `src/history_schema.js`
- `src/history_import.js`
- `src/history_store.js`
- `schemas/cr-review-history-pack-v1.schema.json`
- `tests/history_schema.test.js`
- `tests/history_import.test.js`

기능:

- 현재 33열 양식의 그룹·열 위치·머리글을 함께 확인
- 가져오기 전 미리보기: 인식 열, 누락 열, 실제 행, 중복, 격리 예정 행
- 오류행 격리와 폐쇄망 내부 오류사유 파일 생성
- 원본 파일 SHA-256, 적재버전, 건수 기록
- 별도 IndexedDB 저장과 `.crhistory` 백업·복구
- 앱 업데이트 후 스키마 마이그레이션 및 롤백 가능한 백업
- 폐쇄망에서 확정한 열·코드 매핑을 `history_config`에 저장해 버전 업데이트 후에도 재사용
- `.crupdate` 설치 시 내부 이력·설정·라벨의 변경 여부를 사전 표시

완료 기준: 같은 파일 재적재 시 중복이 늘지 않고, 중간 오류가 다른 행을 막지 않으며, 새 앱 버전에서도 이력자료와 내부 설정이 유지돼야 한다. 모든 백업·복구 파일은 폐쇄망 안에서만 보관한다.

### P2. 저위험 편의기능

- 계약명·상대방·부서·유형·기간으로 과거 검토 검색
- 입력 화면에서 사용자가 선택한 이력의 계약명·신청유형·신규/변경/연장·배경을 사전채움
- DB 값, 문서 자동추출값, 시스템 추론값, 사람 확정값을 나란히 표시
- 개인정보/업무위탁 값은 ‘과거 신청/검토 기재’로만 표시하고 현재 적용범위의 정답으로 쓰지 않음
- 변경·연장 사건은 명시적 연결 또는 높은 신뢰도의 후보만 제시하고 사람이 원계약을 확정
- 과거 검토결과는 원문 인용과 함께 참고카드로 표시하되 자동판정을 바꾸지 않음

완료 기준: 사전채움 수락률, 수정률, 이력검색 성공률, 잘못 연결된 계약군 수를 폐쇄망 내부에서 계측할 수 있어야 한다. 계측 이벤트에는 계약 원문이나 자유서술을 중복 저장하지 않는다.

### P3. 사람 검증 골드셋

초기 표본은 폐쇄망 UI가 실제 이력에서 150~200건의 후보를 계약유형·부서·신규/변경/연장·난이도·개인정보/업무위탁 상태로 층화 추출한다. 경계·부정·불일치 사례 50건 이상을 별도로 포함한다. 표본 ID·원문·라벨은 폐쇄망 저장소에만 남긴다.

라벨 단위:

- 최종 계약유형과 대안 유형
- 적용범위 및 불확실 사유
- 검토할 체크항목과 검토 불필요 항목
- 해당 조항 또는 계약 전체 의견 여부
- 계약서 수정, 계약 외 확인, 협상 가능, 별도 조치 없음의 최종 처리
- 과거 검토 재사용 가능 여부와 계약군 연결

전체의 20% 이상은 두 사람이 폐쇄망 안에서 독립 검토하고 불일치를 조정한다. 조항 근거가 없는 자유서술은 체크매칭 정답이 아니라 검색·쟁점 후보용으로만 쓴다. 앱 업데이트 때마다 표본을 다시 넣지 않도록 골드셋은 `history_benchmarks`에 버전 독립적으로 보존한다.

### P4. 오프라인 성능평가와 shadow 운영

데이터 분할은 무작위 행 분할이 아니라 시간순 분할을 기본으로 하고, 같은 계약군·같은 파일 지문·사실상 동일한 템플릿은 한쪽 세트에만 둔다.

| 과제 | 핵심 지표 |
|---|---|
| 유형분류 | 적용가능 건 비율, macro-F1, Top-2 재현율, 사람 변경률 |
| 계약군 연결 | Precision@1, no-link 오탐, 사람 확정률 |
| 유사검토 검색 | Recall@3, MRR, 무관 후보 카드 수 |
| 적용범위 | 상태별 정밀도·재현율, 필수 이슈 누락 건수 |
| 체크·조치 | 불필요한 수정요청률, 필요한 조치 누락률, 사람 역전률 |
| 편의성 | 최초 유효 이슈 확인시간, 총 검토시간, 클릭·수정 횟수 |

현재 v1.49.0의 내부 실행결과를 폐쇄망 기준선으로 저장하고, 새 `.crupdate`를 설치할 때 동일한 내부 표본을 다시 실행하여 비교한다. 비교화면은 앱 버전·엔진 해시·표본 수·지표와 악화 항목을 폐쇄망 안에 기록한다. 합성 2천 건 처리 성공은 처리성능 검증일 뿐 의미 정확도의 근거로 사용하지 않는다.

외부로 피드백이 허용되는 경우에도 기본 반출물은 만들지 않는다. 사용자가 명시적으로 선택한 때에만 행 단위 정보가 없는 `진단 요약`을 생성하며, 다음만 포함한다.

- 앱·스키마·엔진 버전과 오류코드별 건수
- 충분히 큰 집단의 집계 정확도·처리시간
- 누락된 기능과 재현용 합성 시나리오 설명

계약명·상대방·부서명·작성자·날짜·파일명·검토결과·태그 근거·표본 ID는 포함하지 않는다. 회사 정책상 집계 반출도 금지되면 이 기능을 사용하지 않고 내부 승인 결과만으로 운영한다.

### P5. 제한적 보조모드 승격

폐쇄망 관리자 화면에서 기능별로 독립 승격한다. 예를 들어 계약군 후보는 매우 높은 정밀도를 충족할 때만 기본 노출하고, 유형은 Top-2 후보와 근거만 제시하며, 적용범위·체크·최종조치는 계속 사람 확인을 요구한다. 필수 이슈 누락이나 잘못된 확신 표시가 증가하면 즉시 shadow로 되돌릴 수 있어야 한다. 외부 개발환경에서 기능을 원격 활성화하거나 내부 데이터를 조회하는 경로는 두지 않는다.

잠정 운영 문턱:

- 가져오기 중 무음 누락·덮어쓰기 0건
- 명시적 ID 기반 파일 연결 성공률 99% 이상
- 계약군 자동 후보 Precision@1 98% 이상
- 유형 macro-F1이 기준선보다 개선되고 필수유형 누락이 증가하지 않음
- 유사검토 Recall@3 개선과 동시에 무관 후보 노출량이 증가하지 않음
- 검토시간 중앙값 20% 단축 또는 확인 클릭 수의 유의한 감소
- 필수 계약조치 누락과 잘못된 자동확정 0건

수치는 실제 표본의 크기와 오류비용을 확인한 뒤 확정한다.

## 6. 우선 개발 백로그

1. 외부 개발환경에서 33열 양식 기반 진단기·오류코드·합성 시험자료를 구현한다.
2. 원천시스템의 검토 ID·파일 ID·이전 검토 ID·제출/완료 시각을 매핑할 수 있도록 폐쇄망용 산출 확인표를 제공한다.
3. `cr-review-history-pack-v1` 규격과 가져오기 미리보기를 코드만 담은 `.crupdate`로 반입한다.
4. 폐쇄망에서 실제 약 2천 건의 품질진단을 실행하고 열·코드 매핑을 확정한다.
5. 별도 IndexedDB, 폐쇄망 내부 백업·복구, 복사 후 전환 방식의 스키마 마이그레이션을 구현한다.
6. 검색·선택 사전채움·계약군 후보를 먼저 제공한다.
7. 폐쇄망에서 층화 골드셋을 만들고 v1.49.0 기준선을 동결한다.
8. 태깅 결과와 비태깅 이력을 폐쇄망 안에서 `review_id`로 결합하되, 태그는 후보 재정렬과 근거검색에만 사용한다.
9. 내부 기준을 통과한 기능만 폐쇄망 관리자 승인으로 shadow에서 assist로 승격한다.

## 7. 착수 전 확인할 핵심 질문

- 원천시스템에 화면에 보이지 않는 내부 검토번호와 첨부파일 ID가 존재하는가?
- 변경·연장 건이 이전 검토번호 또는 원계약 번호를 보유하는가?
- `검토결과`는 화면 텍스트인가, 첨부 의견서 내용인가, 둘의 조합인가?
- 완료 건 외 취소·반려·진행중 건을 평가 모집단에서 어떻게 다룰 것인가?
- 작성자·신청자 이름을 가져올 필요가 있는가, 부서와 가명화 ID로 충분한가?
- 브라우저 저장소 삭제에 대비한 내부 승인 백업 위치와 복구 담당자는 누구인가?
- 집계 오류코드·정확도 수치조차 외부 반출이 금지되는가, 아니면 승인된 비식별 집계만 가능한가?
- 폐쇄망에서 업데이트 전후 내부 벤치마크를 실행하고 승격을 승인할 담당자는 누구인가?

위 질문 중 식별자·첨부 연결·발생시점이 해결되기 전에는 정확도 학습 단계로 넘어가지 않는다. 외부 반출 허용범위가 정해지지 않으면 기본값을 ‘어떠한 진단자료도 반출하지 않음’으로 둔다.

## 8. v1.50.0 구현 결과

외부 개발환경에서 실제 내부 행을 사용하지 않고 다음 P0·P1·P2 기반 기능을 구현했다.

- 33열 한 시트의 신청 영역과 검토결과 영역을 분리하는 가져오기
- 머리글 33개 일치 확인, 범위행 제외, 원천 검토번호·임시 ID·누락·날짜 형식·신청/결과 충돌 진단
- 별도 IndexedDB인 `contract-review-history`와 멱등 병합·리비전 보존
- 폐쇄망 내부 `.crhistory` 백업·복구 및 브라우저 영구저장 요청
- 계약명·상대방·부서·유형·기간·검토번호 검색
- DB 유형을 현재 계약유형에 연결하는 폐쇄망 설정과 선택 이력의 입력 참고
- 현재 계약의 유형·적용범위·수정 필요를 과거 값으로 자동 확정하지 않는 안전 경계
- 과거 이력을 선택한 검토의 최초 자동유형과 사람 최종유형을 앱 버전별로 누적하는 내부 평가
- 최신 legal-opinion-tagger 문서대장의 신청·결과 분리 열과 문서별관계 시트 호환

검증 결과는 Node 422건, Python 102건, 빌드 스모크 테스트 전부 통과다. 합성 계약검토 이력과 합성 태깅자료는 앱 재로딩 및 `.crupdate` 설치 뒤에도 각각 1건이 유지됐다. 사용자가 제공한 빈 산출요청 양식은 계약서 검토 시트, 머리글 33/33, 범위행 1건, 실제 데이터 0건으로 정확히 인식했다.

아직 실제 데이터가 있어야만 수행할 수 있는 업무는 폐쇄망 현장진단, 실제 코드값 매핑, 안정적 검토번호 존재 확인, 사람 골드셋 구성, 유형 외 적용범위·체크·최종조치 정확도 평가다. 이 단계의 결과는 앱 저장소와 내부 백업에만 남기며 외부 업데이트 파일에 포함하지 않는다.
