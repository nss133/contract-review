# contract-review — 계약서 리뷰 가이드

보험사 법무팀이 계약서를 검토할 때 확인해야 할 사항과 관련 원문을 짚어주는 **오프라인 단일 HTML 앱**.
최종 결론은 도구가 아니라 검토자가 `이상없음 / 검토의견`으로 남긴다.

팀 배포용 설명은 [팀원용 사용안내](docs/TEAM_USER_GUIDE.txt)를 바탕으로 만든 Word 문서이며,
배포 ZIP에 `contract-review-user-guide-v{버전}.docx`라는 이름으로 자동 포함된다.

- 기본 모드는 완전 오프라인: 브라우저만으로 실행, 네트워크 요청 0건
- 화면 효과는 `시스템 설정 / 효과 사용 / 효과 줄임` 중 선택하며, `효과 사용`은 관리형 PC의 동작 줄이기 설정보다 우선
- 선택형 로컬 AI도 외부 전송 0건: localhost의 Ollama만 호출
- 규칙 기반 매칭: 다신호 점수 + 신뢰도 tier + 구조화 태그 trace로 "왜 이 항목이 떴는지" 항상 설명 가능
- 증적 중심: 모든 체크 항목에 근거 조문 원문(quote)이 붙고 빌드 시 DB와 대조 검증

## 바로 써보기

빌드 없이 완성본을 열려면 `dist/contract-review.html`을 브라우저로 열면 된다. (커밋된 최신 빌드)

규칙 엔진만 사용할 때는 위 HTML을 그대로 열면 된다. 로컬 AI 교차검토를 함께 사용하려면
Ollama에서 `qwen3:4b` 또는 `qwen3:14b`를 실행할 수 있는 상태로 두고 아래 로컬 서버를 시작한다.

```bash
python3 build/serve_local.py
# → http://127.0.0.1:8765
```

앱의 `로컬 AI 교차검토`를 켜면 규칙 엔진이 고른 Top-K 후보를 선택한 qwen3 모델이 의미 기준으로
교차검토한다. 서버는 `127.0.0.1`에만 바인딩되고 Ollama도 `127.0.0.1:11434`로만 호출한다.
계약서가 외부 네트워크로 전송되지는 않는다. 로컬 서버나 Ollama가 없으면 기존 규칙 결과를 유지한다.
충족도는 지식 파일에 사람이 확정한 `llm_elements`가 있는 항목만 판정한다. 모델이 `있음`으로
답해도 근거 인용이 실제 후보 조항에 포함되지 않으면 인정하지 않으며, 요소 정의가 없는 항목은
관련성 안내만 제공한다. AI 코멘트 초안은 검토자가 `초안 사용`을 눌러야 최종 판정에 반영된다.

## 아키텍처 — "빌드 타임에 무겁게, 런타임에 가볍게"

지능이 필요한 일(지식 큐레이션, 조문 원문 대조)은 빌드 단계(Python)에서 하고,
브라우저 안에서는 예측 가능한 규칙 기반 매칭만 돈다.

```
knowledge/*.yaml (체크리스트 지식, 사람 검수 대상)
        │
build/build_html.py
   ├── validate.py         스키마·정규식·심각도 규칙 검증
   ├── enrich.py           data/law_snapshot.sqlite에서 조문 원문(quote) 대조·첨부
   └── src/*.js + *.css     인라인 조립
        ▼
dist/contract-review.html  (단일 파일, 외부 의존 0)
```

런타임 JS 모듈(브라우저 인라인, 외부 의존 0):
`sim.js`(유사도 char_wb TF-IDF·Jaccard) → `clause_role.js`(조항역할·규범유형) →
`contract_tags.js`(구조화 태그 브리지) → `legal_constraints.js`(법령상 이상조합 경보) → `scope_assessment.js`(법규 적용범위) → `matcher_config.js`(임계값) → `segmenter.js`(조항 분할) → `matcher.js`(점수·tier) →
`pf.js`·`cfb.js`·`extract-*.js`(파일 추출: PDF·DOC·HWP·HWPX·DOCX) →
`action_router.js`(계약서 수정·별도 자료 확인·회사 유불리 검토 안내)·
`verify.js`·`assessment.js`(시스템 평가 원장)·`local_llm.js`(Ollama 보조)·`verdict.js`·
`loop.js`(지식 루프)·`goldset.js`(내장 골드셋)·`tags.js`·`formal.js`(형식 점검) → `app.js`(UI). 이 순서로 인라인된다.

### 법규 적용범위 판정 — Scope Engine

체크리스트를 매칭하기 전에 `scope_assessment.js`가 법규의 적용범위를 별도로 판정한다. 현재
`금융기관의 업무위탁 등에 관한 규정`은 계약서의 “위탁·대행” 단어만으로 켜지지 않고,
`금융업 영위 목적 / 제3자 용역의 계속적 활용 / 단순 후선·집행업무 제외`를
각각 확인하여 `적용 / 비적용 / 확인 필요` 중 하나로 분류한다.

예를 들어 단건 행사대행·대관·숙박·차량 용역은 조달 유형으로 분류하고 금융업무위탁 체크 13건을
붙이지 않는다. 반대로 1년간 상시 보험상담 콜센터나 보험금 청구·심사 운영은 계약 유형과 무관하게
횡단모듈 `X-FINOUT`을 켜고 해당 체크셋을 불러온다. 제목·파일명·본문을 함께 사용하며 확정 가능한
상태는 한 줄로 접고 `확인 필요`일 때만 미해결 질문을 펼친다. 사람이 원하면 `판정 수정`에서 네 요소를
바꿀 수 있고, 자동 근거와 수정값은 `system_assessments.scope_assessments/scope_answers`에 보존된다.

보험상품 설명·가입권유가 행사 실행용역에 섞인 드문 조합은 업무위탁이나 모집계약의 양성 신호로
사용하지 않는다. `legal_constraints.yaml`이 보험업법 제83조·제99조의 모집 자격·위탁 제한과 제98조,
시행령 제46조의 특별이익 금지를 별도 준법경보로 올린다. 경보는 계약 유형을 바꾸지 않으며,
금융업무위탁 scope는 비적용으로 유지한다. 명시적 모집 주체(GA·보험대리점·설계사·위촉계약)가 있으면
금융업무위탁 규정은 비적용으로 두고 해당 계약 유형의 체크리스트로 검토한다.

### 구조화 태그 매칭 — 검수 항목만 제한 보조

`legal-opinion-tagger`의 계약 전용 프로필을 로컬 브리지로 가져와 조항과 체크항목을
`주제·주체·행위·대상·규범강도·조건` 축으로 비교한다. 예를 들어 “수탁자는 개인정보 처리업무를
재위탁하려면 위탁자의 사전 동의를 받아야 한다”는 문장은 `재위탁/수탁자/재위탁/개인정보/사전동의`로
구조화되어, 단순히 “재위탁”이라는 단어가 같은 항목과 “개인정보 재위탁의 사전동의” 요건이 같은 항목을 구분한다.

`shadow`와 `assist` 골드셋 51건을 모두 통과한 16개 `curated` signature만 제한 가감점으로 사용한다.
필수 축이 빠지면 가점하지 않고, 태그는 후보 재정렬과 설명을 돕는 신호일 뿐 노출 게이트나 자동판정의
독립 근거가 아니다. 검토자가 조항을 확인·재지정하면 정답·오답 조항의 구조태그가 원문 없이 코퍼스에
누적된다. 표본 5건·반복률 80%를 넘은 변경안만 사람 승인 후보로 제시하며, 승인안도 다음 배포의
`shadow↔assist` 회귀테스트를 통과해야 반영된다. 설정·승격 기준은
[구조화 태그 매칭 운영설계](docs/structured-tag-matching.md)에 정리되어 있다.

개인정보 체크에는 문장별 `주제+행위+금지` 태그를 결합한 관계 게이트를 추가했다. 따라서 보안관리약정서의
“제3자에게 제공하여서는 아니 된다”는 실제 제3자 제공이 아니라 처리위탁 보호조항으로 읽는다. 반대로
`제공받는 자·그 이용목적·제공 동의`가 확인되면 제3자 제공 관계로 분류하고, 계약 문구가 아니라
동의서·고지자료 같은 외부 증빙을 확인하도록 안내한다. 표준 보안관리약정서가 커버하는 세부 보호조항은
검토 화면에서 하나의 묶음으로 접어 체결·첨부·작성항목 완성 여부만 확인한다.

### 법률검토 전 건 태깅자료 — 최초 1회 적재·버전 독립 보존

`legal-opinion-tagger`의 일괄 XLSX에서 `문서대장·문서별태그·태그정본·태그별근거·태그연결성`
5개 구조화 시트를 읽어 별도 IndexedDB `contract-review-workspace`에 저장한다. 중복 원문이 있는
`원본+태깅결과` 시트는 다시 저장하지 않는다. 같은 문서 ID와 같은 내용은 멱등 제외하고, 같은 문서 ID의
태깅 결과가 달라지면 과거본을 지우지 않고 리비전으로 보존한다.

폐쇄망에서는 `최초설치_계약서검토_실행기.html`을 한 위치에 두고 계속 사용한다. 최초 설치와 이후
업데이트는 실행기에서 `contract-review-v{버전}.crupdate` 파일을 선택한다. 실행기 URL이 바뀌지 않으므로
앱 코드만 교체되고 태깅자료·계약검토 상태 저장소는 유지된다. 브라우저 데이터 삭제나 프로필 변경에
대비해 `지식 데이터 > 지식팩 백업`으로 `.crknowledge` 파일을 폐쇄망 내부에 보관한다.

적재된 자료는 당장 계약유형·체크노출·자동판정을 바꾸지 않는다. 먼저 태그 빈도·동시출현·결론 연결을
shadow 자료로 집계하고, 계약검토 연결 후보가 사람 승인과 회귀검증을 거친 경우에만 후속 버전의
유형 별칭·적용범위·체크 signature에 반영한다.

## 검토 설정 — 국면·유형·모듈 (입력 단계에서 지정)

분석 전에 입력 탭에서 세 가지를 지정한다. 본문을 넣으면 자동 추정값이 프리필되고, 검토자가 그 위에서 조정한다
(**사람의 지정이 기계 추정보다 우선** — 분석 시작이 수동 선택을 덮어쓰지 않음).

| 설정 | 뜻 |
|---|---|
| **당사 지위(국면)** | `계약 당사자` = 당사가 의무를 부담·이행 / `수익자·투자자` = 펀드·신탁에 투자자로 참여 |
| **계약 유형** | 체크리스트 세트를 결정(업무위탁·IT외주·투자·NDA 등 9종) |
| **적용 모듈** | 규제 레짐 단위 on/off(개인정보·전자금융·하도급 등) |

금융기관 업무위탁 규정처럼 별도 적용요건이 있는 모듈은 모듈 칩 위의 **적용범위 카드**에서
결론과 근거어를 먼저 확인한다. 계약 문언에 없는 사실은 부정으로 추정하지 않으며, 경계사례는
`확인 필요`로 남긴다. 검토자가 요소별 답을 바꾸면 체크리스트가 즉시 다시 계산된다.

### 문서 제목과 당사 지위 — 분류의 1차 신호

계약의 성격은 **제목**에 가장 뚜렷하게 드러난다. 담보권 설정계약은 제목부터 티가 나고
("근질권설정계약서"), 반대로 신탁계약서가 "질권 설정 시 전자등록의 방법으로 한다"고
방식만 정한 경우 그 문서는 담보설정계약이 아니다. 앱은 표제 줄을 뽑아 유형 감지·모듈 활성·
체크 적용 전반에서 최상위 가중치로 쓴다. 읽어낸 제목과 **계약상 당사 지위**(질권자·수익자·
위탁자 등)는 입력 탭에 표시되므로 검토자가 확인할 수 있다.

당사 지위도 함께 본다 — 같은 담보설정계약이라도 어느 자리에 있느냐로 볼 것이 갈린다.
당사가 **담보를 잡는 쪽**(질권자·채권자)이면 "대항요건·점유이전을 갖추었는가"를 보고,
**담보를 제공하는 쪽**(설정자·물상보증인)이면 "제공 조건이 과도하지 않은가"를 본다
(유질 약정 유무, 피담보채무 범위·채권최고액 특정, 구상권 보전, 처분제한 범위).
다만 갑·을만 쓰고 상호를 적지 않은 계약서가 흔하므로 **지위를 못 읽었을 때는 게이트를
걸지 않는다**(모름을 근거로 접으면 누락검출을 잃음). 지위가 겹쳐 읽히면 양쪽 관점을
모두 보여준다 — 덜 보여주는 것보다 더 보여주는 쪽이 안전하기 때문.

**국면(stance)이 왜 필요한가** — 같은 문언이라도 *당사가 그 규범의 수범자인지*에 따라 검토 관점이 뒤집힌다.
투자신탁의 신탁계약은 집합투자업자·신탁업자 사이의 펀드 단위 문서이고 당사는 수익자일 뿐인데,
본문의 "자산운용"·"대주주·계열회사"·"모집" 문구만 보고 보험업 자산운용 규제를 붙이면
**당사가 준수주체인 양** 엉뚱한 체크리스트가 된다(2026-08-04 실사고).
`수익자·투자자` 국면에서는 그런 당사자 전제 모듈이 통째로 빠지고,
대신 "수익자에게 불리한 조항이 없는지"를 보는 항목(수익자총회 결의·반대수익자 매수청구권·
운용사 면책조항 등)이 올라온다. 리포트 첫머리에도 이 관점이 배너로 고정 표시된다.
사모 요건 부합처럼 **수범자가 판매회사·운용사인 항목**은 수익자 입장에서 직접적이지 않으므로
반영 여부 확인 수준(참고)으로만 표시한다.

예외가 하나 있다 — 계약 상대방이 **미래에셋 계열사**(예: 미래에셋자산운용이 운용사인 펀드)면
수익자 국면이라도 계열사 거래 이슈가 실제 발생하므로 해당 검토가 가동된다.
판정은 법인명 기준이라 펀드 상품명의 브랜드("미래에셋맵스…투자신탁")만으로는 켜지지 않는다.

## 변경합의서 검토 — 원계약 첨부

변경합의서·개정합의서를 검토할 때 **원계약 첨부**로 원계약 파일을 넣으면 그 내용을 전제로 판정한다.
원계약이 이미 다루는 항목은 "빠진 항목"이 아니라 `원계약에 반영`으로 분류되어 알람에서 빠지고,
검토 포커스는 변경된 내용에 남는다. 원계약을 넣지 않으면 변경합의서 본문만으로 판정한다.

## 검토 결과 남기기 — 판정 2종

각 항목에 남기는 검토 결과는 두 가지다.

| 판정 | 뜻 | 부가 |
|---|---|---|
| **이상없음** | 이 계약서에서 문제 없음 | 사유 선택(선택사항): `반영되어 있음` / `해당사항 없음` / 미선택 |
| **검토의견** | 보완·수정이 필요함 | 의견 메모 |

`해당사항 없음`을 독립 판정으로 두지 않고 **이상없음의 사유**로 둔 이유: 우리 케이스와 무관해서
문제가 없는 경우를 별도 판정으로 찍으면 "체크 항목 자체가 부적절하다"는 뜻으로 읽힌다.
결과는 어느 쪽이든 "이상없음"이고, 그 이유가 반영되어 있어서인지 해당사항이 없어서인지만 다르다.
이전 버전으로 남긴 `해당없음` 판정과 팀원 회신 파일은 불러올 때 자동 이관된다.

판정 아래의 `정확도 개선용 피드백`을 펼치면 `실제 처리 결과`를 선택할 수 있다.
이 항목은 기본으로 접혀 있는 선택 입력이며, 선택하지 않아도 검토 완료와 리포트에는 영향을 주지 않는다.
`계약서 수정 요청 / 문제 문구 삭제 요청 / 현 문구 유지 / 별도 자료·절차로 확인 /
이 계약에는 해당 없음 / 추가 확인 후 결정` 중 실제 처리한 결과를 선택하면 시스템의 권장 처리와
사람의 결론이 함께 코퍼스에 누적된다. 이미 입력한 항목은 다시 확인하기 쉽도록 펼친 상태로 표시된다.
기존 `이상없음 / 검토의견`은 법무 결론, 실제 처리 결과는 그 결론을 어떻게 실행했는지를 뜻하므로 서로 대체하지 않는다.

### 계약서 반영 안내

법적으로 확인할 가치가 있다는 사실과 계약서 문구를 실제로 고쳐야 한다는 결론을 분리한다.
부재점검 119건 전부는 `contract_actions.yaml`에서 사람이 확인한 정본으로 관리한다.
각 항목은 계약 명시·조건부 명시·회사 유불리 검토·계약문구 불요와 실제 확인 위치를 함께 갖고,
새 부재점검이 이 분류 없이 추가되면 빌드가 실패한다. 따라서 일반 법령 체크를 곧바로
`계약 명시 필요`로 단정하지 않으며, 계약문구가 아닌 약정서·증적·내부통제에서 볼 항목도 분리한다.

검토자가 `실제 처리 결과`를 남기면 시스템 권장 처리와의 쌍이 코퍼스에 누적된다. 화면의
`계약서 반영 안내와 실제 처리 비교`는 수정·삭제·별도 자료 확인처럼 실행결과가 비교 가능한
표본만 일치율로 계산하고, 회사 유불리 검토와 추가 확인 후 결정은 분모에서 제외한다.

| 화면 분류 | 의미 |
|---|---|
| 계약서 수정 검토 | 필요한 계약 문구가 확인되지 않아 추가·수정 여부를 확인함 |
| 문제 문구 삭제·수정 검토 | 계약에 있으면 안 되거나 그대로 두기 어려운 문구를 확인함 |
| 별도 자료에서 확인 | 보안관리약정서·동의서·고지자료·내부통제·점검증적에서 확인함 |
| 회사 유불리 검토 | 법정 필수문구는 아니며 회사에 유리한 조건으로 협의할지 살펴봄 |
| 계약서 수정 불필요 | 문구가 이미 확인됐거나 계약 문구가 이행요건이 아님 |
| 계약서 반영 여부 확인 | 계약서 반영 필요성 또는 현재 문구의 충분성을 사람이 확인함 |

### 시스템 평가와 사람 판정의 분리

검토의견 JSON에는 사람의 최종 판정(`verdicts`)과 별도로 규칙 엔진의 사실 평가
(`system_assessments`)가 기록된다. 시스템 평가는 적용성, 근거 발견 상태, 후보 조항,
검토 경로를 담는다. 문장 요건이 없는 참고 항목의 확정 매칭과, 참고·권장 항목 중 사람이 정의한
보수적 문장 요건을 통과한 경우에는 `이상없음(반영되어 있음)`이 자동 기재된다. 균형성·법적 효과처럼 판단이 필요한
복합 체크는 증거를 찾더라도 자동 기재하지 않으며, 검토자가 언제든 판정을 바꿀 수 있다.

부속서류에서 직접 확인한 항목은 `covered_by_subdoc`, 계약서가 별첨 체결을 참조하거나 검토자가
별첨 반영을 선언한 항목은 `referenced_subdoc`으로 따로 기록한다. 따라서 계약 본문에서 문구를
찾지 못한 진짜 부재알람과 부속서류 반영분을 코퍼스 분석에서 구분할 수 있다.

로컬 AI 결과도 규칙 판정을 덮지 않는 `advisory`로 기록된다. `direct / reference_only /
unrelated` 관련성과 `complete / partial / unclear` 충족도를 남기고, 사람 판정과의 조합을
코퍼스에 축적해 향후 항목별 자동화 승격 여부를 평가한다.
`complete / partial`은 사람이 정의한 필수 요소와 원문 인용 검증을 통과한 경우에만 사용한다.

관리모드(`#admin`)의 `골드셋 채점 > LLM 기여 분석`에서 같은 `document_id`의 예측 파일과
사람 정답 파일을 불러오면 `LLM 교정 / LLM 악화 / 둘 다 정답 / 둘 다 오답`을 항목별로
확인할 수 있다. 배포 ZIP의 `matching-labeling-form.html`은 블라인드 골드 템플릿을 직접
불러와 사람이 관련 조항을 선택하고 정답 JSON으로 저장하는 오프라인 폼이다.

관리 구역의 `블라인드 골드 템플릿`과 `실험 예측 내보내기`는 규칙 Top-1 대비
qwen3:4b Hybrid의 매칭 정확도를 쌍대 측정하는 별도 실험 파일을 만든다. 누적 코퍼스와
섞이지 않으며 실행·채점 기준은 [매칭 LLM 실험 프로토콜](docs/experiments/matching-llm-protocol.md)을 따른다.

사람 판정에는 `origin`이 함께 기록된다. 직접 판정(`manual`), 일괄 처리(`bulk`),
부속서류 자동 기재(`subdoc`), 전년 판정 수용(`prior_review`), 구 데이터(`legacy`)를
구분해 축적하므로 체크별 자동화 가능성과 사람의 교정 패턴을 나중에 평가할 수 있다.

2026-08-06 실험 시작점에서 구버전 내장 seed와 브라우저 누적 코퍼스를 초기화했다.
이후 검토 결과를 새로 적재하면 빈 코퍼스에서 다시 누적된다. 기존 백업 파일은 복원 실험용으로 별도 보관한다.

## 계약서 입력 — 붙여넣기 또는 파일

계약서 텍스트를 붙여넣거나 **파일 열기**로 불러온다. 지원 형식(전부 브라우저에서 파싱, 외부 요청 0):
`.docx`·`.hwpx`(zip+XML) · `.pdf`(pdf.js, 텍스트층 있는 PDF) · `.doc`(Word 97-2003, CFB) · `.hwp`(한글 5.0, CFB+deflate).
스캔 PDF·암호 문서·구형(3.0) hwp는 자동 추출 불가 — 텍스트를 복사해 붙여넣는다.
추출기·벤더(pdf.js·JSZip)는 [legal-review-finder](../legal-review-finder)의 검증된 코드를 이식했다.

## 개발 환경

- Python 3 (표준 라이브러리 + `pyyaml`, `pytest`)
- Node.js (테스트 러너 `node --test`만 사용, 추가 패키지 없음)

## 빌드

```bash
python3 build/build_html.py
# → dist/contract-review.html + dist/contract-review-v{버전}.zip(배포용) 생성
```

빌드는 `data/law_snapshot.sqlite`(리포에 커밋된 조문 스냅샷)에서 조문 원문을 읽는다.
**원본 DB 없이 클론만으로 빌드된다.** (스냅샷 구조는 아래 "데이터" 참조)

### 버전 관리

루트 `VERSION` 파일이 단일 소스 — 빌드가 앱 상단바·푸터 표기, 배포 zip 파일명,
내보내기 JSON(`meta.app_version`)에 자동 주입한다. 부여 규칙: **팀 피드백 라운드
반영 시 minor**(예: 10차 = 1.10.0), 버그·데이터 소수정은 patch. 릴리스 절차 =
`VERSION` 올리고 재빌드 — zip 파일명이 곧 배포본 식별자.

python3 -m pytest tests/          # 빌드 파이프라인 (validate·enrich·build)
node --test tests/*.test.js       # 런타임 로직 (sim·clause_role·matcher·segmenter)

## 데이터 — 스냅샷과 원본 2계층

체크리스트 지식(`knowledge/`)은 조문 원문을 근거로 인용하는데, 그 원문은 대용량 SQLite DB에 있다.
DB 전체(수백 MB)를 리포에 넣지 않고, **지식이 실제 인용하는 조문만 추출한 스냅샷**을 커밋한다.

- `data/law_snapshot.sqlite` — 앱이 쓰는 조문만 담긴 소용량 스냅샷. **커밋 대상.** 팀원은 이것만으로 빌드 가능.
- 원본 DB — 새 조문을 인용해 지식을 확장할 때만 필요. 로컬 전용(리포 밖). 경로는 `build/config.py`의 `EXTERNAL_LAW_DBS` 참조.

**지식에 새 조문을 인용한 경우** 스냅샷을 갱신해야 원문이 붙는다 (원본 DB가 있는 환경에서):

```bash
python3 build/extract_snapshot.py   # 지식이 인용하는 조문을 원본 DB에서 스냅샷으로 재추출
# → data/law_snapshot.sqlite 갱신 후 커밋
```
